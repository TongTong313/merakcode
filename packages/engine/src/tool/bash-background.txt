Starts a long-running bash command in the background and returns immediately with a job ID. Use this for commands that would block the agent for minutes or hours; the agent can keep working while the command runs.

When to use this instead of bash:
- Dev servers (e.g. `npm run dev`, `bun run dev`, `python manage.py runserver`)
- Build watchers (e.g. `tsc --watch`, `vite build --watch`)
- Long compilations or test runs that the user does not need synchronous output from
- Any command the user explicitly asks to run "in the background"

When NOT to use this:
- Short commands (< 30 seconds): use `bash` instead so the agent can read the result and react
- Commands whose output you need to inspect right now: use `bash`
- Anything that needs interactive stdin: not supported

Output handling:
- The command is launched immediately. The tool returns a `jobId` and a brief confirmation message.
- The job's stdout and stderr are kept in memory (last ~500KB only); the tail is included in the completion message.
- The job runs until it exits, is stopped, the server stops, or its timeout passes. The timeout is 30 minutes unless
  you pass `timeout` (milliseconds); pass `timeout: 0` for dev servers and watchers that should keep running.
- At most 10 jobs run at once; starting another fails until one ends.
- When the job exits, its final status (completed / failed / stopped), exit code and tail output
  are automatically delivered to you as a new user-style message. Do not wait or poll for it —
  just continue with other work and react to the completion message when it arrives.

The user can stop a running job from the UI (`POST /bash/jobs/:id/stop`, a process-tree kill); you do not call it.

Usage notes:
- Always provide a clear, concise `description` (5-10 words) so users can recognize the job in lists.
- The `workdir` parameter has the same semantics as the regular bash tool: defaults to the project root, never use `cd` in the command itself.
- Once a background job is started, do NOT call this tool again with the same command unless the user explicitly asks. Spawning duplicate dev servers will cause port conflicts.
- The agent should usually mention the job ID in its reply so the user can track it.
