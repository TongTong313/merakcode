# 智能体架构思考

这份文档是我对 MerakCode v1.0.0 重构的产品设想和架构关键点，合并了几轮讨论得出的结论。它回答“要做成什么、为什么”；具体怎么做（模块、接口、切片、测试）在 `docs/plans/v1-agent-engine.html`，那份是设计方案，这份是它的源头。两份文档冲突时以设计方案为准，并回头改这份。

## 1. 目标与定位

MerakCode v0.3 是一个 AI 编程工具。v1.0.0 要把它升级成**纳管所有智能体 Harness 的入口**。这里的 Harness 指 Claude Code、Codex、opencode、pi 这类智能体运行体，也包括 MerakCode 自带的。用户在 MerakCode 里既可以用自带的智能体干活，也可以把电脑上装的各家智能体拉进来，让它们在一个群里被同一个编排者指挥、受同一套权限和沙箱管束、向同一个任务看板汇报。纳管所有产品的 Harness 是我的终极目标。

产品形态有四条线：

- **单聊**：和一个执行者一对一，像现在一样。它是引擎内核的试金石。
- **协作群**：多人多智能体协同，以任务驱动、以事件触发。
- **本地优先，云端增强**：一台电脑、一个用户，不依赖任何云端就能完整使用，包括本地群。云端群提供跨设备、多人和账号。
- **编码为主，兼顾其他**：主要场景是写代码，但事件、任务、工作区的模型不假设一定有 git 仓库，团队做一份 PPT 或一组文档也能用。

技术上：引擎用 Go 重写，原创，不复制 v0.3 的引擎代码，也不复制任何一家的代码（可以参考它们的思路，但要做得比它们更好）。前端复用现在的 Electron 桌面端。SDK 用 TypeScript，因为调用方是 Electron。命令行是和桌面端平级的产品形态。日志、诊断包和 CI 从第一天就有。

## 2. 核心概念

- **Leader（编排者、队长）**：负责一个顶层任务（或群的日常事务）的编排者：理解目标、拆任务、派工、收报告、向人请示和汇报。群有一个默认 Leader，每个顶层任务可以指定别的 Leader。默认是 MerakCode 自带的，也可以指定外部产品担任。代码里叫 `Leader`。
- **Worker（执行者）**：接任务、干活、交报告的智能体。MerakCode 内置一种，外部产品经适配器也是 Worker。代码里叫 `Worker`。
- **线程**：一条 Leader 会话加它的调度器。群线程处理没有任务归属的事；每个顶层任务一条任务线程。一个 Leader 成员可以同时领导多条线程。
- **成员**：协作群里的参与者，人和智能体都是成员。智能体成员有角色（Leader 或 Worker）、拥有者、所在设备、种类；人类成员有群角色（拥有者、管理员、审批人、普通成员、观察者）。
- **档案**：描述一个智能体成员是谁的一份数据：角色说明、职责、系统提示词、模型、工具池、权限模式、预算。内置成员用默认档案不需要配置；外部产品必须有一份，Leader 靠它判断谁适合做什么。
- **协作群（群）**：人和成员一起干活的长期单位，创建时选本地或云端。群里可以开很多任务。
- **任务**：群里的工作项。人建的是顶层任务（一个目标），Leader 拆出来的是子任务。每个顶层任务有自己的 Leader 和工作周期。
- **认领**：一个成员接下一个任务，对应一条会话和一块工作区。成员可以排队认领多个，一次只做一个。子智能体不是成员，不能认领。
- **工作区**：一次认领干活的地方，四种形态：git worktree、普通目录、原地（带租约）、无。
- **事件**：一件发生了的事实，有统一的公共字段。来源三类：引擎内部、项目环境的变化（有人改了仓库，哪怕没用 MerakCode）、外部系统。事件只追加不修改。
- **存储宿主**：连上引擎并负责存盘的客户端：桌面端主进程、命令行、云端服务。
- **群状态**：一份压缩过的群的状态：目标表、任务表、成员表、做过的决定、等人回答的问题。它是每条 Leader 线程上下文的主体。
- **快速通道、慢速通道**：明确有执行方的事由代码直接送达，不经过模型；需要判断的事才让 Leader 的模型来。
- **半双工、全双工**：半双工是智能体一干活就听不见新消息，像对讲机；全双工是操作进行中仍然有响应，新输入在下一个推理边界被处理，像电话。
- **哨兵**：引擎里按固定规则巡检的代码：卡住的认领、死掉的进程、原地打转的工具调用、失联的宿主、烧得太快的预算。只发事件和通知，不调模型。
- **收件箱、任务看板**：每个人自己的待办和通知；按状态排列的任务卡。两者都从事件算出来。

## 3. 一套引擎，两种角色

MerakCode 自带两种角色，复用同一套引擎。它们不是两套代码，而是同一套引擎装上两份不同的档案：

- **Leader** 拿到所有注册的成员，针对人的需求拆任务、派给合适的成员、汇总结果返回给人，在关键节点向人请示。它要非常聪明，模型配最强的，但它不参与任务的完成，所以工具池以管任务为主：建任务、派任务、发消息、问人、按 id 查资料、记决定、请求合并，外加读写群的共享文档（写计划、写决定）和只读项目代码（拆任务时要看代码长什么样）。它没有写代码和跑命令的工具。
- **Worker** 完成 Leader 下发的任务，和 Claude Code、Codex 类似，工具池丰富：读写文件、搜索、命令行、网络。在群里再叠加汇报进度、交报告、问 Leader、按 id 查资料。

外部产品经适配器成为 Worker：Claude Code、Codex、opencode、pi 各用自己的原生接口接（stream-json、app-server、ACP、RPC 模式），其他支持 ACP 的智能体用通用的 ACP 适配器，连 ACP 都没有的走纯命令行。外部 Worker 的群工具经 MCP 挂载进去。外部产品也能当 Leader：把编排工具经 MCP 暴露给它，队长提示词由 MerakCode 给，事件摘要作为消息送达。

引擎必须具备类似 Claude Code、opencode 的模块：agent 循环、上下文管理、记忆、会话、事件总线、工具调用、模型服务、权限与沙箱。能力对标，实现原创。

**存算分离**是硬要求：引擎只负责智能体的执行过程，自己不写盘。它做的每件事都变成一条带固定字段的事件发出去，连上来的存储宿主负责落盘并确认；引擎需要历史时向宿主要。三种宿主用同一种存储格式，桌面端写的数据命令行能读。客户端必须通过 SDK 和协议使用引擎，不能直接调用引擎内部。

**引擎通用消息**：引擎内部只有一种消息格式（消息由 Part 组成：文字、思考、工具调用、工具结果、图片、文档）。各家大模型服务商的协议格式只存在于它们各自的客户端包里，在包的边界上双向转换，服务商 SDK 的类型不出包。

## 4. 任务驱动与事件触发

绝大多数智能体以对话驱动：发一个 prompt，智能体干活。单聊保留这个形态。协作群以**任务**驱动：人添加任务、描述任务，Leader 编排、下发、汇总，全过程可控、人类可观察。人也可以随时在群里发言干预执行路径，这要求整个系统能实时动态响应，也就是**事件触发**：智能体的每条消息、人的发言、人建的任务、代码的变化、产物的生成、外部系统的通知，都是事件，群的行为由事件驱动。

这就是我希望 MerakCode 具备的**主动意识**：一个项目里任何事件，产品的变化、代码的变化、用户在群聊里随便发的一句话，可能并没有指定谁来做；规则能确定的事由快速通道直接处理；规则确定不了的事，Leader 发现需要解决就直接安排解决，并回复人类对应的文本。群建好以后默认就有一个群聊界面。主动的程度由群设置控制（保守、默认、积极）。

Leader 是任务级别的，因为我们是任务驱动：不同任务可以有不同的 Leader。每个顶层任务一条线程，群级别另有一条群线程处理没有任务归属的事。线程之间并发；线程内通道是全双工的、推理是单线程的：每个回合很短、从不在回合里等任务或等人；新事件在步与步之间插进来；人的发言可以打断正在进行的模型调用；人发言后立刻有代码层的回执；事件多了就合并、批处理、限流、按预算节流。两条代码层的直达：人 @ 某个成员的话直接给它；人在某个任务讨论串里的发言直接给做这个任务的成员。哨兵负责发现卡住、死进程、原地打转和预算异常。

## 5. 协作群的完整流程

先拉群，再开任务。建群时第一个选项是本地还是云端，建好后不能互转。本地群的宿主是本机，只能加本机成员；云端群的宿主是云端，Leader 在云端跑，成员可以来自任何设备，即使全是本机成员也走云端。客户端永远只连本机引擎，本机引擎负责连云端，桌面端不需要知道一个群是本地的还是云端的。云端服务是单独仓库里的程序，可以在本机以开发模式部署，一台电脑就能测通云端群。

一个群是长期的，可以有多个目标同时进行；人和成员在群级别加入；任务卡可以把参与者缩小到群里的一部分人和成员。

完整流程：A 在客户端建群（本地或云端），拉人和成员进来，设目标仓库或目录 → A 开一个任务，指定或默认一个 Leader → 任务线程拆解成任务卡、放进任务池、派给合适的成员（成员忙就排队）→ 各成员在各自的工作区干活，过程事件实时可见 → 人随时在群里发言干预、做关键决策、收任务进展 → 成员交固定格式的报告 → Leader 判断合格与否，请求合并或发布产物，必要时请人审核 → 顶层任务走完规划、实施、集成、审核、交付的状态机（审核不通过可以回到实施或规划）→ 完成后 Leader 向 A 交总结。

引擎随启动者生死：桌面端彻底退出（不是关窗口进托盘），本机引擎也退出，正在跑的本地任务标为中断并记录进度；云端群的 Leader 和别的设备上的 Worker 继续跑。想要人不在电脑前也能接活，把引擎装成系统服务。

## 6. 任务认领与冲突解决

任务只有两条路被认领：Leader 派工，人点名。暂不做成员主动揭榜，入口统一从 Leader 走。只有群里的 Worker 成员能认领；Leader 或 Worker 自己开的子智能体不是成员，不能认领任务。一个成员一次只执行一个任务，但可以排队认领多个；一个任务可以多人协作（主做加评审、范围分工、接力），范围重叠的协作认领会被任务池拒绝。

多个智能体写同一个仓库怎么解决冲突，分三层：事前，任务卡写明大概碰哪些文件，派工时尽量不重叠；事中，每个认领在自己的工作区里干活，写代码的任务用 git worktree 物理隔开；事后，做完的改动进合并队列一个一个合并回目标分支，真冲突了自动生成一个集成任务派给一个成员解决。worktree 的代价是依赖目录要各装一份，后面用“认领开始时跑安装命令”和“复用上一个 worktree”优化。

不是每个任务都需要 worktree：做 PPT、整理文档这类任务用普通目录，产物发布到群的产物库等人审核；不能隔离的场景原地干活并持有租约；调研、回答问题这类任务不需要工作区。

## 7. 权限与安全

现有产品默认全部放行、高度自主，这不安全。MerakCode 的做法分三层：

- **三档模式**，沿用 v0.3.1：每次询问、仅询问危险行为、全面接管。前两档下成员进程都在系统沙箱里，本机没有可用沙箱时逐次询问；全面接管关闭沙箱，所有操作放行，失败的命令不自动重跑，出了问题由选它的人负责，界面要明说。仅询问危险行为模式下，群里的常规审批可以先由任务线程的 Leader 代答，Leader 拿不准再问人。
- **系统沙箱兜底**：所有成员进程，包括 Claude Code、Codex、opencode、pi、ACP 智能体和纯命令行程序，都跑在 MerakCode 的系统沙箱里：读不了凭据目录，只能写工作区和缓存目录，碰不了 `.git/hooks` 这类保护路径，只能连允许的网络。就算一个外部产品绕过了我们的权限门（它跑的是自己的循环），也出不了圈。
- **按角色路由审批**：人有群角色，不同的事需要不同的角色来批（常规写入找审批人，工作区外的改动找管理员，合并到目标分支和超预算找拥有者）。需要人判断的事由引擎送到有对应角色的人的收件箱，跨设备时经云端。外部 Leader 批审批也受同一张路由表限制。本地单人使用时这个人持有全部角色，这是现阶段的 mock，但角色检查是真的。

## 8. 上下文、记忆与模型

**上下文管理**要做到：平时省 token、对话丝滑，到阈值时大幅压缩但不丢关键信息，还要命中缓存。三条总原则：大的工具输出在进入历史之前就截断落盘，历史里只留头尾和引用；一旦进了历史的消息、系统提示词、工具列表不再原地修改，要变就追加；到阈值一次性把最老的一段重建成结构化摘要，保留近几轮原文。这三条同时满足缓存前缀匹配，也是 Anthropic 最新模型对“保留思考块”的硬性要求。配套的还有：阈值有上界（90%）和下界（压到 60%，但至少保留近几轮）；大文件分多次写；工具池按需加载但服务商看到的工具列表全程不变（延迟工具经 `load_tools` 和 `call_tool` 使用，任何服务商都不会因此失效缓存）；每次请求都记录预算分配和缓存命中。

**记忆**和上下文的区别：记忆要落盘，是长期的，要能在 agent 循环里动态加载。分成员、群、项目三个作用域。进入上下文有三条路：会话开始时按情境召回；干活过程中模型主动找，或读到有笔记关联的文件时自动附上；任务结束时提取新笔记。所有进存储的笔记过密钥扫描。

**模型**模块要兼容 v0.3 的八家服务商（OpenAI、Anthropic、Google、DeepSeek、Moonshot、智谱、阿里、OpenRouter），按线协议只有三种，三个客户端覆盖。要支持多模态输入（图片、PDF）。消息由 Part 组成，流式输出的增量是 Chunk，Chunk 折叠成 Part。思考强度六档：关、低、中、高、特高、最高，映射到各家自己的参数，模型目录记每个模型支持哪几档。模型目录提供价格、上下文窗口、能力：内置表加在线刷新加用户覆盖加中转站匹配。Anthropic 用官方 Go SDK 接，但它的类型只在那一个包里出现。

**工具**对标 Claude Code 和 opencode，基础工具一样不少，包括后台运行的子智能体。判断什么该做成工具：模型主动发起的动作做成工具（可拦截、审批、渲染、审计、并行）；引擎替模型做的内务（压缩、召回、截断、权限、沙箱）不做成工具。

## 9. 云端服务

云端服务以后会建，先在本机以开发模式部署测试，再放到阿里云。它提供账号体系、云端群的中转和存储、云端 Leader、成员的注册和分享（分享只有“自己用”和“分享给群”两档）。多人都可以发言、建任务、注册自己的智能体。权限由群角色管控。云端 Leader 调模型用用户自己托管的密钥，先不计费；它的只读代码工具下发到有仓库检出的设备上执行。

云端代码放在单独的仓库，引用本仓库的公开包。已决定：服务端用 AGPL-3.0 开源（可自部署对“纳管入口”这个定位很重要），客户端保持 MIT，部署配置、防滥用规则、计费对接留私有，先私有，等协议稳定、开发模式跑过一轮真实使用再公开。

## 10. 产品形态与技术选型

- **引擎**：Go 程序 `merak`，放在仓库根目录的 `merak/`，和 `apps/`、`packages/` 并列，按 Go 的布局范式来：模块根目录放 `go.mod`，入口放 `cmd/merak`。`engine/` 和 `protocol/` 是公开包（云端服务要引用），其余在 `internal/` 下。不用 cgo，一台机器编出六个平台。标准库优先；已同意加 SQLite 的纯 Go 驱动和 Anthropic 官方 Go SDK，系统凭据库到云端阶段再核实。
- **日志与诊断**：标准库 `log/slog`，NDJSON 落盘并轮转，每行带会话和事件 id，密钥自动脱敏；`merak diagnose` 一键打包日志、版本、脱敏配置，桌面端有导出按钮。
- **CI**：沿用现有工作流骨架，三个系统的矩阵：静态检查、脚本测试、TypeScript 包测试、Go 测试（Linux 上加竞争检测）、六平台编译冒烟；沙箱一致性测试在三个系统上真跑；最后一个聚合 job 作为合并门禁。
- **桌面端**：复用现有 Electron 前端，要新增群聊、任务看板、收件箱、审核四类视图，都从事件算出来。
- **命令行**：独立的产品形态，有自己的存储宿主和中英双语文案，机器可读输出，对外开放给其他产品接入；还提供 ACP 服务让 MerakCode 自己也能被编辑器纳管，提供 MCP 服务让外部产品拿到群工具和编排工具。
- **SDK**：TypeScript，类型从 Go 生成；三种接入方式（协议、SDK、命令行）背后是同一个引擎。
- **存储**：桌面端和命令行共用一个数据目录里的 SQLite 文件和一份建表语句；云端用 PostgreSQL 实现同一套契约。
- **协议**：JSON-RPC 2.0 跑在本机 WebSocket 上，双向，连接时先交换版本。

## 11. 已经定下的原则

- 一套引擎两种角色；Leader 是任务级别的；事件是唯一事实来源；存算分离；群在创建时选本地或云端；客户端只连本机引擎；引擎随启动者生死；引擎内只有一种消息格式；子智能体不能认领任务。
- 分阶段、垂直切片：每个切片从入口切到引擎底层，做完就多一个用户看得见的能力。五个阶段：地基与单聊内核、服务化与存算分离、纳管与本地协作群、主动性与安全、云端。
- 测试先行：一次一个会失败的测试，让它通过，再写下一个；测行为不测实现；不用 mock。
- 杜绝过度设计：字段按切片加，接口有了两个实现才抽象，常量先写死，不预留，不写规则语言。
- 不读、不复制 v0.3 的引擎代码；可以参考它的目录名和概念。参考其他产品的思路，不复制代码，并且要做得更好。

## 12. 已定的几个细节

- Leader 的并发由任务级线程天然解决：每个顶层任务一条线程，线程之间并发，不需要再升级。
- 子智能体在后台运行，结果作为追加消息回到父会话；第一版允许嵌套一层。
- 文件监视器先用轮询（每 5 秒，只用标准库）；项目文件数超过五万或一次扫描超过一秒时哨兵提示，再接系统文件通知接口。
- 云端服务仓库在阶段 2 结束后起步，第一版只做设备链接协议的服务端和 SQLite 开发模式，正式部署放在阶段 5 之后。
