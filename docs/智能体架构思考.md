这个代码仓库我计划用go进行重构，MerakCode的目标是统一纳管各类智能体Harness，这里的Harness指比如Claude Code、ChatGPT、OpenCode等智能体。因此我选择了用go语言来写，这里面涉及到云服务的一些东西。我计划是从简单往复杂开始，针对智能体引擎单独写一个方案放到docs的plan文件夹里面，可以参考另外一个地基plan文件。这里我把想重构的智能体引擎架构的关键点跟你说，然后你帮我看看如何设计一个具体的重构方案：

# 1. 编排+执行双Harness架构

对于MerakCode来说，要自带两套不同的智能体Harness，他们复用同一套底层引擎，其中：
1. 编排Harness：我们需要一个Harness，这个Harness的任务就是编排，它能够拿到所有注册的智能体。需要注意，这里会涉及到本地使用和跨端使用的问题。如果用户仅在本地使用，也就是联动它自己电脑里面的claude code、codex这些（当然联动若干个merakcode本身也完全可以），则就默认使用本地的merakcode的编排harness，用于针对用户的需求进行任务的指派，把他们分给不同的Harness去做，每个智能体Harness都可以配置角色、系统提示词这些，可以根据这个来分配谁来做什么任务。除了指派任务，这个编排Harness还需要汇总结果并返回给用户。理论上，这个编排Harness是需要非常聪明的，要配置好模型，但它本身不参与任务的完成，所以他的工具池不一定要特别丰富。对于想跨不同端实现多智能体多人协同，那就需要一个云端服务，我们计划是在云端也放一个编排Harness，它能够把各端注册的智能体放到一个群组，人类也可以加入这个群组，主要是在关键节点审核产物给与下一步操作的指引，云端需要同步智能体的执行情况，是不是每个merakcode的使用者都得有一个守护进程？如果是完全本地的使用，是不是也得有一个守护进程来看整个群聊的执行状态？
2. 执行Harness：顾名思义，这个Harness就是用来针对编排智能体下发的任务进行完成，这就跟claude code、codex这些智能体比较类似，需要具备比较丰富的工具池，能够完成比较复杂任务。注意，merakcode提供我们内置默认的一种执行harness，我们纳管的各类智能体产品也视为一种执行harness。

当然，由于merakcode本身带一套完整的智能体引擎，由共同的一套智能体引擎构建上述两套harness，其中编排harness仅仅用于多人多智能体协同场景（简称群聊），执行harness用于单聊和群聊场景当中。所以这套智能体引擎需要具备类似claude code、opencode的模块，至少包括agent loop、上下文管理、记忆、会话管理、事件总线、工具调用、大模型服务等模块，当然也要具备调用其他智能体harness CLI的可能。注意这里，我们强调一点，我希望merakcode重构以后的harness具备“存算分离”的特点，也就是我们只负责智能体的执行过程，对于落盘的操作，仅根据引擎的事件或者是其他东西，由客户端完成存储落盘的行为。和merakcode之前的版本一样，客户端必须调用SDK来实现，不能够直接调用引擎。所以智能体架构方案里面首先要实现一套基于go语言的强大的智能体引擎，可以参考claude code、codex、opencode、pi等的思路，但我们还是希望原创一下！

面向群聊场景，这个里面有一个非常关键的问题就是上下文管理，我们必须有一套完备的群聊上下文管理系统，编排Harness需要把对应的上下文送到每个执行harness里面，这里面包含对话信息、记忆信息、公共信息、文档信息等等，这个非常重要。另外就是，编排harness因为要汇聚结果并安排下一个阶段的工作（直到任务完成），所以它需要汇总各执行harness的上下文，这个量太大了，很容易就把编排harness的上下文撑爆了，所以这里的关键就是怎么设计一个机制，能够让编排harness的信息也是可控的。比如说，执行harness的全量信息都落盘存储，但有一些索引机制，可以按照比如task id、session id、event id（正好对应下面的任务驱动和事件触发）等索引到对应关键的信息？同时要注意，在执行过程中，每个执行harness之间先认为他们不通信，所有的交流都要通过编排harness来记性转发和发送。整个群聊人类对话的也只是编排harness，所以编排harness需要具备受到消息立即反应的特点，而不能像一般智能体一样还在排队消息啥的。


我设想的整个思路完整的多端多人多智能体协同流程是：A用户在客户端构建协作群，拉人和智能体进来 -> 发送任务 -> 编排智能体进行编排 （纯本地则本地智能体编排，涉及到多人多端则云端编排智能体进行编排） -> 编排智能体下发任务给各端执行Harness -> 人类可以在中间发送消息对执行过程进行管控，也可以做关键决策，也可以收到当前任务执行的关键信息 -> 任务完成编排智能体汇总信息发给A用户

# 2. 任务驱动与事件触发

现在绝大多数的智能体都是通过对话的形式作为驱动形式，也就是用户发一个prompt，然后智能体干活。merakcode的单聊功能自然具备这个，但我们希望增加智能体协作群，这个协作群是以任务而不是prompt为主要驱动。具体而言，用户可以通过添加任务的方式，对任务进行描述，然后送给编排Harness来做编排并下发各智能体开始干活（这里需要注意，以新建任务为主，可以在任务的基础上拉很多群聊解决问题，当然也可以先建群聊然后绑定任务，任务最终是在人机协作群聊里面解决问题），最后汇总结果。所以我希望这个任务能够全过程可控，人类可以观察这个任务执行的全过程。这个就叫做任务驱动。当然，人类也可以通过对话的形式，在智能体工作过程中发言从而干预当前任务执行的路径，这就需要整个智能体系统具备实时动态响应的能力，这就要提到我们的第二个概念———事件触发。

所以事件触发就是，针对智能体的每一条消息、人类的prompt、人类提供的任务项，代码的变化、任务产物的生成等我们都看作是一个事件，整个智能体群组的行为由各个事件驱动，事件来了以后智能体群组可以主动或者被动的执行对应的任务。这就是我们希望merakcode具备一定的主动意识。

# 3. 揭榜挂帅机制

我设想要构建一个任务池，因为用户的任务可能非常简单就一句话，但我们需要通过编排harness进行分析和拆解，变为很多个子任务沉淀到任务池里面，然后就是靠harness主动派发，或者是人类@的方式，让各个智能体揭榜任务，一个智能体同时只能完成一个任务，但同一个任务可以被多个智能体接走协作完成，这就要求多个智能体之间必须要具备一定的冲突解决机制，都在写同一个代码仓库，那么怎么样解决冲突的问题，这个是核心。

# 5. 补充（2026-11-10）：任务、协作群和产品底线

看了 v1.0.0 第一版的实现以后，我把思路再细化一下，下面这些是现在的要求。

**产品底线。** 相比 v0.x 版本，基本功能不能有任何阉割，这是原则底线。模型支持、MCP（包括远程 MCP 和授权登录）、技能、插件、斜杠命令、计划、和外部产品单聊、撤回和编辑重发这些 v0.x 都有的能力，一个都不能少。前端要对标之前的版本，尤其是对话界面。命令行也一样，v0.3 命令行有的命令 v1 都要有。老用户升级到 v1 时，配置不用重新配，历史对话要尽可能迁移过来，迁过来以后还能接着聊。

**能直接新建的东西。** 现在就是四样：新建对话（单聊，可以选 MerakCode 自己，也可以选纳管进来的 Claude Code、Codex 这些产品）、新建智能体、新建协作群、新建任务。项目组属于更高层级的设计，后面我再设计。目前先限制一下：单聊也好、协作群也好、任务也好，都必须有一个工作空间（项目文件夹），这个是必须设定的，侧边栏下面就按项目文件夹来组织。

**任务和协作群是一对多的关系。** 先简化一下：一个协作群可以做多个任务，一个任务只归属于一个协作群。

1. 可以先新建任务项，但想要启动这个任务，就必须新建一个协作群（或者选一个已有的协作群）去处理它，任务最终是在人机协作的群里解决的。这种情况下，协作群的工作目录和任务相同。
2. 也可以先新建一个协作群去干活：人类说了一个什么问题，Leader 感知到了，就创建一个任务，这个任务就归属于这个协作群。一个协作群可以聊着聊着做出多个任务。协作群主动发起的任务，工作目录就是协作群的工作目录。
3. 一个协作群有且仅有一个 Leader，群里的任务都由它负责。
4. 智能体里只有 Leader 可以创建任务；人也可以手动主动创建任务，不是所有任务都是自动产生的。

**Leader 的拆解要看得见。** Leader 本身具有拆分子任务、列 todolist 的能力，这个拆解和分配要有前端显示，让用户知道谁在干什么。

**人类的指令最高级。** 人的指令高于 Leader 的安排。人可以直接给任何一个成员下达任务，受到安排的智能体必须能够及时响应人的新需求；Leader 需要根据这个事件更新自己的状态和这个任务的状态。

**全双工。** 编排智能体和执行智能体在干活的时候都要能随时接收和处理新消息，这就是我说的全双工的范式，类似 DeepSeek 的 super agent。

**揭榜。** 除了 Leader 派发和人类 @，智能体也可以主动认领任务池里的任务。

**守护进程。** 要有守护进程，不然没法时刻更新任务的状态。

**收件箱。** 收件箱是首页的一个栏目，查看当前这个客户端收到的所有状态消息，比如任务完成提醒、需要我决策的事项，还要有一个右下角弹窗提醒。

**任务看板。** 整体有一个任务看板，打开就能看到这个客户端当前所有任务的情况。已经完成的、过时的要及时清除，用户点击结束的就不再显示，否则越堆越多。

**计划。** 不再有单独的计划模式，任何模式下都可以生成计划。
