MerakCode v1.0.0 当前分支验收复核与整改方案

概要

结论：不通过验收。引擎和 SDK 的单元测试、静态检查全部通过，问题在四处：
  1. 产品模型和要做的产品不一致，方案在几个根本点上偏离了愿景文档（第 2、6 节）。
  2. 相对 v0.x 大面积倒退，违反“基本功能不能阉割”的底线。桌面端重写缩水（消息列表 921 → 284 行，设置页 1272 → 216 行，少了 26 个文件、23 个 e2e spec）；模型目录只剩 11 个内置模型，打开只看得到一家一两个模型；MCP 远程和登录、技能、插件、斜杠命令、计划、LSP、网页搜索、定时任务等十几项能力没有；系统提示词只有一句话（4.5、4.6 节）。
  3. 测试不真实。88 个桌面端 e2e 里 20 个失败，失败的用例被移出了 CI（5.4 节）。
  4. 20 项基础功能缺陷，引擎内部分层也偏离了方案 3.3 节（第 3、5 节）。
引擎内核（循环、会话、工具门、模型客户端、沙箱、存储契约）质量合格，保留。整改按第 9 节的 29 份施工单（R0 到 R26）进行：先修地基和模型目录，再按新的产品模型改协作群和任务，同时补齐 v0.x 的全部能力，然后以 UI 分支为基线恢复桌面端，最后做首页、智能体、协作群、任务的新页面。

复核对象是 dev-v1.0.0 的提交 f195bc2（S0 到 S31、D1 到 D10），对照设计方案 docs/plans/v1-agent-engine.html、最初的愿景文档 docs/智能体架构思考.md、AGENTS.md 和产品负责人 2026-11-10 的三轮答复（第三轮的思路已补进愿景文档第 5 节）。第 7 节的决定已经吸收了这些答复；第 9、10 节是写给执行模型的施工单和执行规则，可以直接交出去。

复核方式：读代码，在 Windows 本机上跑全量测试（结果见 1.1 节），用 git 对照 dev-v0.3.1。没有修改产品代码。第 3 节标“代码确认”的结论可以直接从代码读出，标“需复现”的是代码推断，要在真实应用里确认后果。

2. 产品逻辑的问题

2.1 现在的模型和目标模型

现在的“群”把四件事合在一起：项目、成员名册、聊天、任务池。Leader 绑在任务上（每个顶层任务一条线程），群只有一条群线程，所以一个群只有一个聊天流，任务也离不开群。目标模型里能直接新建四样东西：对话、智能体、协作群、任务，都要选工作空间。协作群和任务一对多：一个协作群有且只有一个 Leader，可以做多个任务；一个任务最多属于一个协作群，Leader 就是这个群的 Leader。单独建的任务（图里的 W）要新建或选择一个协作群才会开始。项目组是更高层级的设计，以后再定。

6.4 守护进程带来的取舍

方案 2.3 节的存算分离是“引擎只算，连上来的客户端负责落盘”。引擎变成守护进程后，桌面端会关掉，但任务要接着推进、事件要接着落盘，所以落盘只能由守护进程自己完成。处理办法：

  • 包的层面不变：engine/ 下的代码仍然不碰磁盘，只通过 store.Store 契约读写；落盘由 internal/localstore 实现，这正是现有 merak serve --store local 的做法，命令行已经在用。
  • 进程的层面改变：本机存储宿主和引擎跑在同一个进程里；桌面端不再当存储宿主。
  • 云端宿主不受影响，仍是一份独立的 store.Store 实现。

这样愿景里“只负责智能体的执行过程，落盘由宿主完成”在代码边界上仍然成立，同时满足“没有守护进程怎么时刻更新任务状态”。顺带删掉一整条远程存储链路和桌面端的原生依赖（7.4 节）。

7. 整改方案

7.1 决策一览

编号 决定 内容
D-1 能新建的东西 四样：对话（单聊）、智能体、协作群、任务。项目组是更高层级的设计，这一轮不做，代码里也不为它预留。代码里协作群仍叫 group，智能体叫 agent
D-2 工作空间必填 对话、协作群、任务各有一个工作空间（项目文件夹），新建时必须选。侧栏按工作空间分组。协作群里的任务和协作群用同一个工作空间（D-6）
D-3 对话（单聊） 本人和一个智能体一对一，智能体可以是 MerakCode 自己，也可以是纳管的产品（Claude Code、Codex 等）；没有 Leader
D-4 协作群 成员来自智能体库，加上本人；有且只有一个 Leader；可以做多个任务，群里的任务都由这个 Leader 负责
D-5 任务 一个任务最多属于一个协作群，一个协作群可以有多个任务（一对多）。任务有两个来源：人在“新建任务”里手动创建，这时它还不属于任何协作群；Leader 在协作群里创建（人在群里提出问题、Leader 判断要做），这时它属于这个群。智能体里只有 Leader 能创建任务，Worker 不能。任务属于某个协作群后才会被推进，所以单独建的任务要启动，必须新建一个协作群或选择一个已有协作群来处理它。任务的归属定下后不再换群；子任务和父任务属于同一个群
D-6 工作空间和 Leader 从协作群来 任务没有自己的 Leader，它的 Leader 就是所属协作群的 Leader；换群的 Leader，群里的任务一起换。工作空间按来源定：
  • 协作群里创建的任务：工作空间是协作群的。
  • 先建的任务新建协作群：协作群的工作空间取任务的，表单里已填好、不能改。
  • 先建的任务交给已有协作群：两边相同就直接归入；不同时协作群的工作空间改成任务的，群里没结束的其他任务一起改。群里还有进行中或排队的认领时不能改，界面提示为这个任务新建一个协作群。
直接改协作群的工作空间也一样：群里没结束的任务一起改，有进行中或排队的认领时不能改
D-7 Leader 线程 每个协作群一条 Leader 线程，群就是 Leader 和人对话的地方；去掉原方案“每个顶层任务一条线程”。群里所有任务（包括子任务）的事件都进这个群的线程；还没有协作群的任务不唤醒任何线程。不设每分钟回合上限：现有的群设置 turnsPerMinute 和它的实现在 R8 删除
D-8 拆解看得见 Leader 拆出的子任务、指派、进度和它的待办列表，在协作群右栏实时显示：谁在做哪一项、做到哪一步
D-9 人的指令最高 人可以在群里 @ 任何成员说话，或直接给任何成员派任务。消息直达这个成员并抢占它当前的一步：能中途收消息的产品立刻送达，不能的停下当前运行、带着人的要求重新开始这次认领。Worker 的提示词规定人的指令优先于 Leader 的安排；同一条消息同时唤醒 Leader，由它更新自己的计划和任务状态。Leader 不得推翻人的指令，有冲突时问人。执行者之间仍不直接通信
D-10 全双工 Leader 和 Worker 干活时都能收消息，新消息在下一个推理边界处理，人的消息可以打断正在进行的模型调用。界面的输入框在回合进行中不锁，发出的消息立刻标“已送达”，处理时标“处理中”
D-11 认领 三条路：Leader 派工、人点名、Worker 主动认领。Leader 拆出的卡可以不指派，留作待认领；空闲的内置 Worker 在它所在的群出现待认领卡时收到一次邀约（一个短回合，认领或放过，每张卡每个 Worker 一次）；任何 Worker 交完报告时能看到所在群的待认领卡并认领；外部 Worker 经 MCP 工具 claim_task 认领
D-12 守护进程 引擎是每个用户一个的后台守护进程，桌面端和命令行都是客户端：谁先启动谁把它拉起来，退出时不带走它；只有显式停止（托盘“停止后台引擎并退出”或 merak stop）才退出。本机存储宿主在守护进程里（--store local），引擎包仍然不碰磁盘；桌面端主进程不再当存储宿主
D-13 收件箱 首页的一个栏目，列出这个客户端收到的所有状态消息：任务完成、待我决策（审批、问题、审核）、受阻、哨兵提醒。新消息在右下角弹窗提醒，点击跳到对应位置；窗口不在前台时同时发系统通知
D-14 任务看板 一个全局看板，列出这个客户端的所有任务，按状态分列。清理沿用 GitHub Projects、Jira、Trello 的通行做法：
  • 已完成、已取消、失败的任务留在完成列，状态变为结束满 3 天后自动归档；天数在设置里可选 1、3、7、14 天或不自动归档，默认 3 天。
  • 每张卡有“归档”：已结束的直接归档；还没结束的先确认，再取消并归档。完成列标题上有“全部归档”。
  • 归档的任务不在看板上，在“已归档”视图里能搜索、恢复，数据不删。
  • 自动归档由守护进程执行，所有客户端看到的一致。
D-15 计划 不再有单独的计划模式。任何权限模式下，智能体都能写计划（工具 write_plan），用户也能要求这条消息先出计划；计划在侧边面板里审阅、编辑，点“执行”或在对话里回复后开始执行
D-16 底线：不倒退 v0.x 能做的 v1 都要能做，以 UI 分支 origin/tt/refactor/ui-side-panel 为对照，一项不少：模型目录、MCP（含远程和 OAuth）、技能、插件、斜杠命令、计划、LSP、网页抓取和搜索、代码搜索、文档解析、定时任务、和外部产品单聊、撤回和编辑重发、对话界面。只有两处变化：计划不再是单独的模式（D-15）；不再提供 v0.3.1 的 adapter-generator 技能，接入别的命令行产品改用 ACP 或纯命令行适配器，不用写代码。对照范围包括 v0.3.1 引擎的文件约定：.merakcode/ 下的规则、命令、智能体、技能目录（消解 C7）

D-18 调用者身份 由连接决定：本机连接是本机用户，云端连接是账号；协议参数里去掉 human（消解 C4）

7.6 模型目录

新的模型目录把 v0.3.1 的做法用 Go 原样补上：

  1. 自动刷新。守护进程启动后在后台刷新：每个配了密钥或地址的服务商（含中转站）拉一次自己的模型列表，公开目录（OpenRouter 免密钥列表）拉一次；之后每小时一次；改了某个服务商的密钥或地址后立刻刷新它。缓存不到 1 小时不重复拉。环境变量 MERAKCODE_DISABLE_CATALOG_FETCH=1 时不联网（e2e 夹具已经设了它）。
  2. 缓存。每个服务商的列表和公开目录各存一份文档（kind catalog），带抓取时间；启动先读缓存，离线也有完整列表。
  3. 合并顺序。用户覆盖 > 服务商实时列表 > 公开目录（按模型 id 补上下文、输出上限、价格、能力、是否弃用）> 兜底表（按服务商和模型族前缀给思考档位、默认档位）> 现有的 11 条内置。
  4. 过滤。每家服务商一条规则，去掉嵌入、重排、语音、图像、审核这类不能对话的模型。
  5. 字段。模型加 deprecated 和 defaultThinking；界面跳过已弃用模型，思考强度默认取 defaultThinking（B16）。
  6. 失败提示。刷新成功发 catalog.refreshed，失败发 catalog.failed（带 MRK 码）；界面重读模型列表，同一服务商同一个错误只提示一次（UI 分支 state/catalog-refresh.ts 的行为）。

做完以后：v0.3.x 格式的插件（本地 .js、.mjs 文件或 npm 包，导出一个返回钩子的异步函数）照样能加载；设置里能添加、看状态、删除。

做法：Go 引擎不能直接运行 JavaScript，所以插件跑在一个单独的插件宿主进程里：一段内置的 JavaScript（用 embed 打进二进制，启动时写到缓存目录）由 Node 运行，加载每个插件，通过 stdio 上的 JSON-RPC 和引擎往来。Node 的来源：桌面端把 Electron 自带的 Node 交给引擎（环境变量 MERAKCODE_NODE 指向 Electron，加 ELECTRON_RUN_AS_NODE=1）；命令行用 PATH 里的 node；都没有时插件状态显示新码“需要 Node.js”。插件宿主和 MCP 服务器一样跑在沙箱里，工作区配置里的插件要经工作区信任确认。

先读：merak/engine/mcp/process.go（子进程和沙箱的写法）、merak/engine/tool/pool.go、merak/engine/loop/loop.go、merak/engine/permission/gate.go；UI 分支 e2e/tools.spec.ts 的插件用例、settings.tsx 的 Plugins。可以读 dev-v0.3.1 的 packages/sdk/js/src/plugin/index.ts 取钩子的名字和参数形状，插件作者写的代码要能不改就加载。

支持的钩子（引擎在这些点调用，插件可以改 output）：

钩子 调用点

chat.message、chat.params、chat.headers 用户消息入史前；发模型请求前改参数和请求头
permission.ask 权限门判定后、问人前，可以改成允许或拒绝

10. 执行规则

写给执行模型。每片开工前把本节读一遍。

  1. 一次只做一片。开工前列出要动的公开接口和要测的行为，然后按施工单“先写的测试”的顺序，一次写一个会失败的测试，运行看到它失败，再写最少的代码让它通过。
  2. 施工单里没写的东西不做。需要施工单没提到的字段、方法、配置、依赖时停下来问，不要自己加。
  3. 不倒退。v0.x 能做的必须还能做。发现施工单没覆盖到的 v0.x 能力，停下来报告，不要删掉或跳过。
  4. 不许为了让 CI 变绿而移走、跳过或改弱测试。测试失败只有两种处理：修好代码；或者写明它由哪一片修，并把它列进 R0 建立的待办清单。把用例挪到不进 CI 的文件，和删掉断言一样，都算违规。
