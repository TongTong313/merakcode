1. 目标和不变的东西

目标：

  1. 引擎分成四层：基础设施、单个智能体、多智能体与人机协同、产品能力。上层可以用下层，下层不能用上层。
  2. 根包 merak/engine 只剩门面和装配，不再放业务逻辑。
  3. 存储的实现全部在引擎之外，引擎只定义接口。
  4. 取消 internal 目录。

不变：

  • 产品行为。
  • 协议在线上的格式：方法名、事件类型名、每条消息的 JSON 字段。
  • 根包对外方法的名字。
  • go.mod 的依赖，不新增第三方模块。

会变：

  • Go 的包路径和引擎的启动参数。
  • SDK 里一部分类型的名字。SDK 的类型名是“Go 包名 + 类型名”拼出来的，类型换了包，名字就跟着变，例如 AgentAgent 变成 DefinitionAgent。只变名字，结构不变。SDK 和桌面端里用到旧名字的地方跟着改名。
  • 几份文档里的布局说明。
不留兼容层。现在用户不多，不为了“老代码不用改”而写多余的代码。类型或函数搬了家，就把所有引用改成新名字；不留类型别名，不留旧名字，不写新旧名字对照表。所有引用都在这个仓库里，Go 和 TypeScript 的编译器会把漏改的地方全部报出来。

2. 术语

词 意思
包 Go 里一个文件夹就是一个包。同一个包里的代码可以互相访问私有内容，不同包只能访问大写开头的名字。
根包 merak/engine/ 这个文件夹本身（不含子文件夹）里的代码。
门面 根包里对外的 Engine 对象和它的方法。服务端只调用门面。重构后门面方法只做一件事：把调用转给对应的模块。
装配 engine.New 创建所有模块并把它们接在一起。只有这里引用全部引擎包。
领域 根包里一组属于同一件事的代码和状态，例如“远程和云端”。每个领域最后变成一个独立的包。
上行引用 下层代码用了上层的函数或类型。这是本方案要消除的东西。
下沉 把一个函数或类型搬到更低的层，让原来的上行引用变成合法的向下引用。
注入 下层定义一个接口或函数类型，写明“我需要这个能力”；上层实现它，装配时传给下层。下层不认识上层。
接入点 注入的一种：对话核心在固定的几个位置调用外面登记进来的函数（S5.4）。

5. 规则

5.1 依赖方向

cmd → cli → server → protocol → engine
storage、cloudlink、migrate、diagnose、testkit → engine
引擎内：feature → collab → agent → infra
  1. 引擎内只能向下引用。同一层的包可以互相引用，但 Go 不允许循环。
  2. engine/ 里的源码不引用 engine/ 之外的本项目代码。唯一例外是模块根包 merak（只有版本号）。测试文件和 testdata 里的程序不受这条限制。
  3. 下层需要上层的能力时，下层定义接口，上层传实现。
  4. 对自己数据的基本操作在下层；给人用的管理流程在 feature/admin。
  5. 不留兼容层（第 1 节）。

5.2 一段代码该放哪一层

问题 答“是”就放
它和智能体的业务无关吗（进程、git、沙箱、日志），或者它是事件、存储接口？ infra
单个智能体跑一个对话就需要它吗？ agent
它是因为有多个智能体或多个人才存在的吗（群、任务、运行器、远程）？ collab
它是因为客户端要展示某个功能，或者给人做安装、卸载、增删改才存在的吗？ feature

按上表从上往下问，第一个答“是”的就是答案。

5.3 存储

  1. 换一台机器也要跟着走的数据（对话、群、任务、记忆、附件），只走存储接口 store.Store。
  2. 密钥只走凭据接口 credential.Vault。
  3. 这两个接口的实现，以及配置文件和日志文件的落盘，都在 merak/storage/。
  4. 引擎直接写磁盘只限两处：用户的项目文件夹，和启动方传进来的工作目录。引擎不自己拼路径，也不退到系统临时目录。

5.4 测试

  1. 每个包自己的测试和源码放在同一个文件夹，这是 Go 的要求。
  2. 驱动整个引擎的场景测试放在 engine/scenario/，按领域分子文件夹。
  3. 多个包共用的测试辅助放在 merak/testkit/。
  4. 同时需要服务端或云端链路的测试，放在 server/ 或 cloudlink/。

6. 执行守则

6.1 红线

  1. 不改产品行为。发现现有行为有问题，记下来告诉用户，不在这次重构里修。
  2. 不改测试的期望值和判断条件。测试文件只允许这几类修改：引用路径；被测的东西改了包、改了名字或改了参数形式时，测试里对应的写法跟着改；文件路径；引擎的启动参数；S8 里的搬目录。
  3. 不跳过、不删除、不削弱任何失败的测试。
  4. 不手改生成的文件（*.gen.go、protocol.gen.ts、schema/ 下的文件）。
  5. 重新生成协议文件（pnpm generate:protocol）之后，必须用第 6.3 节的办法证明只有类型名变了。证明不了就不许提交。
  6. 不留兼容层：不写类型别名（type X = other.X）来保留旧名字，不写新旧名字对照表。
  7. 不往 go.mod 加模块。
  8. 不往根包加新的业务代码。
  9. SDK 和桌面端的代码只允许一种修改：把旧的类型名换成新的类型名。

6.2 每个提交都要过的验收

在仓库根目录运行。全部通过才能提交。

pnpm --dir merak typecheck
pnpm --dir merak test
pnpm check
pnpm test:script
  • pnpm check 里包含 check:protocol。它报“out of date”说明 SDK 的类型名变了，按第 6.3 节处理。
  • 只编译通过不算数，必须跑测试。搬目录这类改动，很多问题（测试里写死的路径）只有运行时才暴露。
  • 本机只能跑本机系统的测试。Linux 的 -race 和三个系统的专属测试由 CI 跑，所以每一步都要开 PR 并等 CI 全绿。
  • TestWindowsSandboxHelperDeathKillsTheMemberTree 在整套测试一起跑时偶尔超时，单独重跑能过。遇到它失败先单独重跑一次；别的测试失败不许这样处理。
  • S3、S6、S7 结束时另外跑一遍桌面端的端到端测试（命令见 CONTRIBUTING.md）。

6.3 SDK 类型名变了怎么办

pnpm check:protocol 报“out of date”时，按下面的顺序做。目的是证明只有名字变了，消息的结构一点没变。

  1. 把下面的脚本存到仓库外的临时位置，例如 /tmp/schema-renames.mjs： 
    import fs from "node:fs"
const [before, after, renames] = process.argv.slice(2).map((file) => fs.readFileSync(file, "utf8"))
let text = before
for (const [from, to] of Object.entries(JSON.parse(renames)))
  text = text.split(`"${from}"`).join(`"${to}"`).split(`/$defs/${from}"`).join(`/$defs/${to}"`)
const sorted = (value) =>
  Array.isArray(value)
    ? value.map(sorted)
    : value && typeof value === "object"
      ? Object.fromEntries(Object.keys(value).sort().map((key) => [key, sorted(value[key])]))
      : value
const same = JSON.stringify(sorted(JSON.parse(text))) === JSON.stringify(sorted(JSON.parse(after)))
console.log(same ? "OK: only type names changed" : "DIFFERENT: more than type names changed")
process.exit(same ? 0 : 1)
  2. 保存旧的协议文件，然后重新生成： 
    git show HEAD:schema/protocol.json > /tmp/schema-before.json
pnpm generate:protocol
  3. 列出哪些名字没了、哪些名字是新的： 
    diff <(grep -oE '^    "[A-Z][A-Za-z0-9]*": \{' /tmp/schema-before.json | sort) \
     <(grep -oE '^    "[A-Z][A-Za-z0-9]*": \{' schema/protocol.json | sort)
  4. 把“旧名字 → 新名字”写成 /tmp/renames.json，例如 { "AgentAgent": "DefinitionAgent", "AgentModelRef": "DefinitionModelRef" }。每个消失的名字都必须对应一个新名字。
  5. 运行 node /tmp/schema-renames.mjs /tmp/schema-before.json schema/protocol.json /tmp/renames.json。必须输出 OK。输出 DIFFERENT 说明结构也变了，这是错误，回去检查这一步的改动。
  6. 在 packages/sdk/src（protocol.gen.ts 除外）和 apps/desktop 里把每个旧名字换成新名字。这些名字都是唯一的大写开头单词，可以整词替换。然后跑 pnpm check，TypeScript 会报出漏改的地方。
  7. 把这张新旧名字表写进提交说明。

如果生成器报“两个不同的类型得到同一个名字”（S0 加的检查），说明两个包里有同名的类型都进了协议。给其中一个 Go 类型改个更具体的名字，不要绕过检查。

6.4 通用改名办法

把一个类型或函数从包 a 搬到包 b 以后，所有写着 a.Name 的地方要改成 b.Name。按下面的顺序做，S1、S4、S6 都用它。

  1. 只替换“包名.名字”这种带包名的写法，并且要求前面不是点号或字母，避免改到别人的字段： 
    sed -i -E 's/(^|[^.A-Za-z0-9_])a\.(Name1|Name2)\b/\1b.\2/g' 文件
    不要替换单独的 Name，也不要替换单独的 a.。
  2. 给用到 b. 的文件加上 b 的引用行，然后 gofmt -w。
  3. 反复运行 go build ./... 和 go vet ./...（vet 会连测试文件一起编译），按报错逐条改，直到两个命令都没有输出。常见的报错和处理：
    报错 处理
    "…" imported and not used 删掉这一行引用
    undefined: b 加上 b 的引用行
    b.Name undefined (type … has no field or method Name) 这个文件里有个局部变量也叫 b，挡住了包名。把那个局部变量改个名字。已知的一处：engine/workspace_mcp_test.go 里叫 definition 的局部变量，改成 server
    import cycle not allowed 不要自己想办法绕，对照这一步的说明检查顺序；解决不了就问用户
  4. 在被搬走的文件内部做替换时要小心三种写法，它们不是对类型的引用，不能加包名：方法名（func (r *Router) Ask(）、结构体字面量里的字段名（Reply{Decision: x}）、点号后面的字段（reply.Decision）。
  5. 这个仓库在 Windows 上很多文件的行尾是 CRLF。改 package 行时不要用 ^package x$ 这种写法，它会匹配不上；用 s/^package x(\r?)$/package y\1/，改完逐个文件确认。

6.5 提交方式

  • 一个小步一个提交。小步的编号是 S4.1、S5.2 这样的。
  • 搬文件用 git mv，保留历史。
  • 提交信息按 CONTRIBUTING.md 的格式，不加任何署名行。
  • 这次重构用户看不到变化，不写 CHANGELOG.md。

6.6 遇到这些情况，停下来问用户

  1. 要让测试通过，必须改测试的期望值或判断条件。
  2. 第 6.3 节的脚本输出 DIFFERENT，并且找不到原因。
  3. 出现循环引用，按这一步的说明和附录 D 的规则解决不了。
  4. 一段加锁的代码同时改了两个领域的状态（S5.3）。
  5. 出现附录 D 没列出的上行引用，并且拿不准该下沉还是注入。
  6. 对话需要附录之外的新接入点（S5.4）。
  7. 附录里的归属和实际代码对不上，并且按规则判断不了。
  8. 仓库里的其他计划文件和本方案冲突。

7. 执行步骤

下面的命令里，M 都是 github.com/TongTong313/merakcode/merak。

S0 协议生成器加撞名检查

为什么：merak/protocol/schema/document.go 用“包名的最后一段 + 类型名”给每个类型起名。两个不同包里的同名类型会得到同一个名字，现在的代码遇到这种情况会悄悄把第二个丢掉。后面要新建 admin/skill、admin/memory 这些和已有包同名的包，必须先有这个检查。

先写测试（新文件 merak/protocol/schema/document_test.go）：

  1. 两个不同的 Go 类型得到同一个名字时，生成失败，错误信息里写出这两个类型的完整路径。
  2. 同一个类型出现多次时照常生成。

再改代码：生成器里记下每个名字属于哪个 reflect.Type。同一个名字第二次出现而类型不同，就返回错误。

验收：第 6.2 节。生成的文件没有任何变化。

S1 包 agent 改名 definition

为什么：腾出 engine/agent/ 这个文件夹名给“单个智能体”这一层用。

  1. git mv merak/engine/agent merak/engine/definition。
  2. 这个文件夹里每个文件的 package agent 改成 package definition（注意第 6.4 节第 5 条）。
  3. 算出这个包对外的全部名字，然后在所有引用它的文件里改引用路径和带包名的写法： 
    names=$( { grep -hoE '^(type|func|var|const) [A-Z][A-Za-z0-9]*' merak/engine/definition/*.go | awk '{print $2}'
           awk '/^(const|var) \($/{b=1;next} b&&/^\)/{b=0} b&&/^\t[A-Z]/{print $1}' merak/engine/definition/*.go

S5.1 建立领域对象

  1. 在根包里给每个领域建一个结构体（私有，名字和领域相同），再建一个公共依赖结构体 core。Engine 里放每个领域一个指针。
  2. core 里放所有领域都只读使用的东西，完整清单见附录 C。每个领域对象都持有同一个 core。
  3. 这一小步只加结构体，不动任何字段和方法。

S5.2 字段归位

  1. 按附录 C，把 Engine 的字段一个领域一个领域地搬进对应的结构体。一个领域一个提交。
  2. 每搬一个字段，把所有 e.字段 改成 e.领域.字段。用编译错误找遗漏：字段从 Engine 删掉以后，所有没改到的地方都会报错。
  3. 字段的类型如果是根包里定义的类型（例如 claimRun），这个类型的归属跟着字段走（附录 D 第二张表）。
  4. 这一小步不改任何逻辑，也不改锁。

S5.3 拆大锁

e.mu 一把锁保护了多份状态：会话表、认领运行表、认领准备表、提问表、合并标记、启动授权、任务审批等。拆成每个领域一把自己的锁。

  1. 每个持有可变状态的领域结构体加一个字段 mu sync.Mutex。
  2. 逐个看 72 处 e.mu.Lock()。看从加锁到解锁之间读写了哪些字段：
    • 全部属于同一个领域：换成那个领域的锁。
    • 属于两个以上领域：停下来问用户。把这一处的文件、行号、涉及的字段列出来。
  3. 持有一个领域的锁时，不许调用另一个领域的方法。需要的话，先把要用的值取出来，解锁，再调用。原来就是这样写的地方保持原样。
  4. 一个领域一个提交。全部换完后删掉 Engine.mu。

这一小步的额外验收：每个提交都要等 CI 的 go test -race 通过，不能只看本机。

S5.4 方法归位

  1. 按附录 A 和附录 B，把每个方法的接收者从 *Engine 改成它所属的领域结构体。例如 func (e *Engine) groupMember(…) 改成 func (r *roster) groupMember(…)。普通函数（没有接收者的）和类型的归属见附录 D 第二张表。
  2. 对外的方法（大写开头）在 Engine 上保留一个同名的方法，方法体只有一行转发：

  3. 领域之间的引用：
    • 高的用低的：高的领域结构体里放一个指向低的领域的指针，直接用。
    • 低的用高的（上行引用）：查附录 D。写着“下沉”的，把被用到的函数或类型搬到表里指定的更低的领域。写着“注入”的，在低的领域的文件里定义一个接口或函数类型，只列它需要的东西；低的领域结构体里放这个类型的字段；在 engine.New 里把高的领域对象赋给它。
