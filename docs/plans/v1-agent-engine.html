MerakCode v1.0.0 智能体引擎与产品升级方案

概要

MerakCode v1.0.0 把一个 AI 编程工具升级为纳管所有智能体 Harness 的入口：用 Go 原创一套智能体引擎，同一套引擎装上不同档案就成为编排者 Leader 或执行者 Worker；Claude Code、Codex、opencode、pi 等外部产品经适配器成为 Worker，也可以担任 Leader；人和智能体在协作群里以任务驱动、事件触发的方式协同；引擎只算不存，桌面端、命令行、云端三种产品形态共用一套协议、SDK 和存储格式。本文是设计方案和施工依据，第 3.9 节是地基施工单，第 15 节是切片表。

总体架构

核心设计决定

  1. 一套引擎，两种角色。代码里编排者叫 Leader，执行者叫 Worker。两者是同一套引擎装上两份不同的档案；Leader 多一个调度器和一套管任务的工具，Worker 多一套改代码的工具。外部产品经适配器成为 Worker，经 MCP 拿到编排工具后也能担任 Leader。
  2. Leader 是任务级别的。每个顶层任务指定一个 Leader，默认是群的默认 Leader，也可以是群里任何一个 Leader 角色的成员。每个顶层任务一条 Leader 线程，群级别另有一条群线程处理没有任务归属的事。线程之间并发，线程内一次只跑一个回合。
  3. 事件是唯一的事实来源，而且事件是通用的。模型输出、工具调用、任务状态变化、仓库里的新提交、一个文件被改动，都是带固定字段的事件。事件不假设在写代码。会话状态、任务池、群状态都从事件算出来。
  4. 存算分离。引擎只产出事件和文档，落盘由连上来的存储宿主完成并确认。桌面端、命令行、云端三种宿主用同一种存储格式。
  5. 群在创建时选本地或云端。本地群的宿主是本机，只能加本机成员；云端群的宿主是云端，Leader 在云端跑，成员可以来自任何设备，即使全是本机成员也走云端。客户端永远只连本机引擎，本机引擎连云端。云端服务可以在本机以开发模式部署。
  6. Leader 线程是全双工的通道、单线程的推理。回合很短且从不在回合里等待；新事件在步与步之间插入；人的发言可以打断正在进行的模型调用；明确有执行方的事走快速通道不经过模型；事件多了就合并、批处理、限流。
  7. Leader 的上下文靠三件事保持可控：群状态、只给编号不给全文、定长的任务报告。
  8. 群是长期的，任务是群里的工作项；认领得到一块工作区，形态按任务定。写代码用 git worktree，做文档用普通目录，只读任务不需要工作区。成员可排队认领多个任务，一次只做一个。子智能体不是成员，不能认领任务。
  9. 权限三档，沙箱兜底，审批按人的角色路由。每次询问、仅询问危险行为、全面接管。前两档下成员进程都在系统沙箱里，沙箱不可用时逐次询问；全面接管关闭沙箱，所有操作放行，由选择它的人负责。
  10. 上下文管理：入史前截断，历史只追加，到阈值整体重建。工具列表全程不变，延迟工具经 load_tools 和 call_tool 使用，任何服务商都不会因此失效缓存。
  11. 引擎随启动者生死。桌面端彻底退出，本机引擎也退出，本地任务标为中断并记录进度；云端群继续跑。

词 意思
引擎 Go 程序 merak 里 engine/ 下的全部代码。智能体怎么跑全在这里，但它自己不读写磁盘。
Harness 一个能独立接任务、干活、交结果的智能体运行体。Claude Code、Codex 是外部 Harness；MerakCode 引擎装上档案也是一个 Harness。
Leader（编排者） 负责一个顶层任务（或群的日常事务）的编排者：理解目标、拆任务、派工、收报告、向人请示和汇报。群有一个默认 Leader，每个顶层任务可以指定别的 Leader。默认是 MerakCode 自带的，也可以是外部产品。
Worker（执行者） 接任务、干活、交报告的智能体。MerakCode 内置一种，外部产品经适配器也是 Worker。
线程 一条 Leader 会话加它的调度器。群线程处理没有任务归属的事；每个顶层任务一条任务线程。一个 Leader 成员可以同时领导多条线程。
成员 协作群里的参与者，人和智能体都是成员。智能体成员有角色（Leader 或 Worker）、拥有者、所在设备、种类；人类成员有群角色（拥有者、管理员、审批人、普通成员、观察者）。
档案 代码里叫 Profile。描述一个智能体成员是谁的数据：角色说明、职责、系统提示词、模型、工具池、权限模式、预算。内置成员用默认档案；外部产品必须有一份。
协作群（群） 人和成员一起干活的长期单位，创建时选本地或云端。一个群有默认 Leader、任务池、群简介、共享文档、一条群事件流，可以开很多任务。
任务、任务卡 任务池里的一条工作项及其描述：要做什么、怎么算做完、碰哪些文件、依赖、工作区形态、要不要人审核、谁是 Leader。人建的是顶层任务，Leader 拆出的是子任务。
认领 一个成员接下一个任务。一次认领对应一条会话和一块工作区。成员可以排队认领多个，一次只做一个。
工作区 一次认领干活的地方，四种形态：git worktree、普通目录、原地（带租约）、无。
会话、回合 一个智能体的一条对话线；从一次输入到模型给出最终回答之间的全过程。Leader 的回合故意很短。
事件、事件流 一件发生了的事实，有统一的公共字段，只追加不改不删。来源三类：引擎内部、项目环境的变化、外部系统。每条会话一本流，每个群一本流。
存储宿主 连上引擎并声明负责存盘的客户端：桌面端主进程、命令行、云端服务。一个引擎同一时刻只有一个宿主。
群状态 一份压缩过的群的状态：目标表、任务表、成员表、做过的决定、等人回答的问题。它是每条 Leader 线程上下文的主体。
调度器 代码里叫 Scheduler。一条线程的事件队列加调度循环：有事件就醒，先走快速通道，剩下的合并后交给模型。
快速通道、慢速通道 快速通道是代码层的路由：明确有执行方的事直接送达，不经过模型。慢速通道是让 Leader 的模型判断。
半双工、全双工 半双工：智能体一旦开始干活就听不见新消息，像对讲机。全双工：操作进行中仍然有响应，新输入在下一个推理边界被处理，像电话。本方案的线程是全双工的，模型一次只处理一批事件。
哨兵 代码里叫 Sentinel。引擎里按固定规则巡检的代码：卡住的认领、死掉的进程、原地打转的工具调用、失联的宿主、烧得太快的预算。它只发事件和通知，不调模型。
收件箱、任务看板 每个人自己的待办和通知；按状态排列的任务卡。两者都从事件折叠出来。
任务材料包、任务报告 派任务时交给 Worker 的开工材料；Worker 做完交回的固定格式结果，有字数上限。
适配器 把外部产品的协议翻译成引擎事件的那层代码。Claude Code 用 stream-json，Codex 用 app-server 的 JSON-RPC，opencode 用 ACP，pi 用 RPC 模式，其他用 ACP 或纯命令行。
沙箱 操作系统提供的进程隔离：限制进程能读写哪些目录、能不能联网。每次询问和仅询问危险行为两档下成员进程都在里面运行。

1. 目标、范围和边界

1.1 产品定位

MerakCode v1.0.0 是纳管所有智能体 Harness 的入口：用户既可以用自带的智能体干活，也可以把电脑上装的 Claude Code、Codex、opencode、pi 和任何支持 ACP 或命令行的智能体拉进来，让它们在一个群里被同一个编排者指挥、受同一套权限和沙箱管束、向同一个任务看板汇报。四条产品线：

  • 单聊：和一个 Worker 一对一。它是引擎内核的试金石。
  • 协作群：多人多智能体协同，以任务驱动、以事件触发。人拉群、加成员、开任务；Leader 拆解、派工、汇总；人随时插话、在关键节点审批。
  • 本地优先，云端增强：一台电脑、一个用户，不依赖任何云端就能完整使用，包括本地群。云端群提供跨设备、多人和账号。
  • 编码为主，兼顾其他：事件、任务、工作区的模型不假设一定有 git 仓库，团队做一份 PPT 或一组文档也能用。

1.2 目标

  1. 用 Go 原创一套智能体引擎，能力对标 Claude Code、Codex、opencode、pi 的内核：agent 循环、上下文管理、记忆、会话、事件总线、工具调用、模型服务、权限与沙箱。不复制任何一家的代码。
  2. 同一套引擎装上不同档案得到 Leader 和 Worker；外部产品经适配器成为 Worker，经 MCP 也能成为 Leader。
  3. 协作群以任务驱动、事件触发：先建群，再开任务；每个顶层任务有自己的 Leader；人随时干预；一切变化都是事件，包括不经 MerakCode 发生的变化。
  4. 引擎存算分离，只算不存。三种宿主共用一种存储格式。
  5. 桌面端、命令行、云端都通过同一套协议和 SDK 使用引擎，任何一种都不直接调用引擎内部。
  6. 日志、诊断包和 CI 从第一天就有：问题能一键打包，每次提交在三个系统上验证。

1.3 不做什么

  • 云端服务本身的代码。它在单独的仓库里；本文只定本地引擎和云端之间的接口以及云端的概念模型。
  • 桌面端的重新设计。桌面端复用现有代码，只换数据来源并新增群相关的视图，见第 14 节的复用地图和第 15 节的 D 切片；新视图沿用现有的设计令牌和组件。
  • 网页端和手机端。它们是云端的客户端。
  • 插件、技能、斜杠命令、LSP、定时任务。工具池和提示词组装为它们留了位置，排在阶段 4 之后。MCP 在阶段 4 做。

2. 总体架构

2.1 一套引擎，两种角色

Leader 和 Worker 九成的机制相同：都跑 agent 循环、都调模型、都发事件、都管会话和上下文。不同的只有角色说明、工具池和调度方式，所以它们是同一套引擎配上两份档案。

档案项 Leader Worker
用在哪 只用在协作群里。群有一个默认 Leader；每个顶层任务指定一个 Leader；一个 Leader 成员可以同时领导多个任务，每个任务一条线程 单聊和协作群
模型 最强的模型，思考强度高；调用次数少，每次上下文大 按档案配置，可以用便宜的模型
工具池 管任务的一套：建任务、派任务、给成员发消息、问人、回复群聊、按 id 查事件和会话、记决定、请求合并、换阶段；读写群的共享文档；只读项目代码。没有写代码和跑命令的工具 改代码的一套：读写文件、搜索、命令行、网络。在群里再叠加汇报进度、交报告、问 Leader、按 id 查资料
调度 每条线程一个调度器：事件队列有事就动，短回合，不阻塞（6.2 节） 一次输入跑一个回合；回合进行中可以收到追加的指示和子智能体的结果
权限 不改代码，不需要文件权限。派任务、关任务、请求合并按群设置可能需要人确认。仅询问危险行为模式下可代 Worker 批常规申请（第 10 节） 按档案里的权限模式：每次询问、仅询问危险行为、全面接管
记忆 群的记忆：决定、约定 成员自己的记忆，加群记忆，加项目记忆
会话 每条线程一条很长的会话，靠群状态和重建控制长度 一次认领一条会话；单聊里一次对话一条会话

外部产品不跑我们的 agent 循环，但对 Leader 来说和内置 Worker 没有区别：能接任务、会发事件、会交报告（5.4 节）。外部产品当 Leader 见 5.6 节。

2.2 本地群与云端群

建群时第一个选项是本地还是云端，建好后不能互转。两条规则贯穿始终：客户端永远只连本机引擎，本机引擎负责连云端；一个群只有一个存储宿主。

本地群 云端群
存储宿主 本机：桌面端主进程或命令行 云端服务。本机引擎只转发和缓存最近一段用于显示
Leader 在哪跑 本机引擎 云端。即使所有成员都在本机也在云端跑
成员来源 只有本机的智能体和本机用户 任何已连云端的设备上的成员；任何账号的人
需要什么 什么都不需要 一个账号，以及一个云端服务：正式的，或者本机开发模式部署的
本机退出时 群停下，任务标为中断 群继续跑；本机名下的认领标为中断，云端 Leader 决定等还是改派
  • 云端群里任何一端的人发言，走“客户端 → 本机引擎 → 云端 → 其他设备的引擎 → 它们的客户端”。本机引擎只中转，不判断。
  • 云端 Leader 调模型用用户托管在云端的密钥（加密存储，调用时解密，不进日志和事件）；云端先不提供模型、不计费。
  • 云端 Leader 的只读代码工具（读文件、搜索）经设备链接下发到持有项目检出的设备上执行，结果回传（13.1 节）。
  • 云端服务是单独仓库里的单独 Go 程序，引用本仓库的公开包 engine/ 和 protocol/。它有开发模式：单个二进制、SQLite、固定开发账号、不要 TLS，在本机跑起来就能测云端群（13.4 节）。

2.3 存算分离：引擎只产出字段，宿主负责落盘

  • “不落盘”指引擎自身的状态：事件、会话、任务、记忆、群状态、档案、配置。工具改用户仓库的文件、建 worktree、写沙箱配置是干活的产物，不算。
  • 工具的超大输出既是产物又要按 id 找回，当作一种 blob 文档交给宿主，引擎只拿到引用（4.9 节）。
  • 一个引擎同一时刻只认一个宿主，第二个声明的被拒绝但仍可作普通客户端。宿主意外断开时，引擎用一层有上限的缓冲兜住（store.Buffered，4.2 节）。

2.4 事件是唯一的事实来源，而且事件是通用的

引擎里发生的每件事都先变成一条事件发布出去，各模块再根据事件更新状态。存算分离、按 id 检索、云端同步、可重复的测试四件事都建在它上面。事件来源分三类：

来源 例子 谁发
引擎内部 模型吐出文字、工具被调用、任务被认领、报告交了、审批请求发出 各引擎模块
项目环境 仓库多了一个提交（可能是人用别的工具提的）、某个目录下的文件改了、检查命令的结果变了 platform/watch 的 git 监视器和文件监视器（9.1 节）
外部系统 CI 跑完了、有人在别的系统里评论了、定时到点了 命令行 merak event emit 或协议方法 event.emit

事件模型不假设有 git：file.changed 是“某个路径下的文件变了”，artifact.produced 是“产出了一个东西”；只有 repo.* 和 merge.* 是 git 专有的，只在工作区形态为 worktree 时出现。五条原则：

  • 发布分两步：先交给宿主，确认写盘后再分发给订阅者。不存在“先改状态再补事件”的路径。唯一的例外是瞬时事件（目前只有 message.delta）：它只给界面边生成边显示用，没有序号，不写盘，直接分发。
  • 状态从事件算出来。会话、任务池、群状态各有一个“应用一条事件”的函数；重放全部历史得到的状态和实时更新得到的完全一样。
  • 两种事件流：session:<id> 记一条会话的全部过程；group:<id> 记群级别的事。认领会话里的事件也带着群 id 和任务 id。
  • 客户端看到的就是这些事件，协议不另设一套“给界面用”的消息。
  • 每个对象都有地址，形如 mrk://group/G/task/T，可以写进提示词、报告和界面链接。

2.5 引擎的生命周期：随启动者生死

谁启动的 什么时候退出 退出时做什么
桌面端 桌面端彻底退出时（托盘菜单的“退出”）。关窗口进托盘不退出，桌面端继续当宿主 固定顺序：停止唤醒 Leader 的模型；向正在跑的本地认领发取消；每个认领记一条 task.updated，状态为“中断”，附进度；等宿主确认全部事件写盘；存会话快照；发 engine.shutdown；退出。超过 10 秒强制退出，没写完的事件下次启动时按宿主的最后序号补对账
命令行 merak serve Ctrl-C 或 merak stop
系统服务（以后 merak service install） 随系统。人不在电脑前也要接活的用户用这个
  • 启动：桌面端先尝试连接，连不上就启动一个。一个数据目录一个引擎进程，端口和令牌写在数据目录里一个只有当前用户能读的文件中。

3. Go 工程布局与地基

3.1 模块位置与公开包

Go 官方布局只有三条：模块根目录放 go.mod；程序入口放 cmd/<程序名>/main.go；不让别的模块引用的代码放 internal/，这是编译器强制的“本模块私有”。Go 的范式里没有 apps/ 这一层，所以 Go 模块放在仓库根目录的 merak/，和 apps/、packages/ 并列，模块路径 github.com/TongTong313/merakcode/merak。

包分两类：

  • 公开包 merak/engine/... 和 merak/protocol/...：云端服务要引用它们（云端 Leader 跑的就是 engine/leader，设备链接的消息类型在 protocol），将来别的 Go 程序也可能引用。v1.0.0 打标签之前接口可以随便改，云端仓库按提交的伪版本引用。
  • 私有包 merak/internal/...：命令行、协议服务端、命令行的存储宿主、云端链接、基础设施。它们是 merak 这个程序自己的实现细节。公开包可以 import 私有包（同一模块内允许），外部模块引用公开包时私有包只是被一起编译，不需要也不能直接 import。

不把 go.mod 放仓库根目录：那样整个仓库都是 Go 模块，go vet ./... 会扫进 node_modules。两个世界各占一个目录：merak/ 是 Go，其余是 TypeScript。仓库工具链要认识这个目录，改三处：pnpm-workspace.yaml、knip.json、script/release/version.ts，见 3.9 节。

3.4 两个进程、一个 SDK

  1. 桌面端启动时运行 merak serve，Go 引擎作为单独进程在后台运行。
  2. 用户在界面输入；界面代码调用 TypeScript SDK 的函数；SDK 把调用变成协议消息，经本机连接发给引擎。
  3. 引擎接口层收到消息交给引擎，跑 agent 循环；每做一步发一条事件回去；SDK 收到后交给界面显示。
部分 负责什么 不负责什么
Go 程序 merak 全部业务逻辑：会话、模型、工具、权限、沙箱、协作群、配置；命令行界面；命令行场景下的存储宿主；诊断包 图形界面
Electron 主进程 窗口、托盘、通知、自动更新、文件对话框、启动和拉起引擎、桌面端场景下的存储宿主 业务逻辑
Electron 界面进程 显示和交互，通过 SDK 调用引擎 读引擎的文件，自己做权限判断
@merakcode/sdk 协议的 TypeScript 客户端，类型从 Go 生成；存储宿主接口和 SQLite 参考实现；看板和收件箱的折叠函数 业务逻辑

不把 Go 编成库给 Electron 调用：需要 cgo 和 Node 原生扩展；引擎崩溃会带崩界面；命令行和桌面端无法共用同一个引擎进程。

3.6 Go 代码规则

  1. 一个目录一个包，包名和目录名相同，小写、简短、单数。按业务领域分包，不按技术层分包，不用 utils、common。
  2. cmd/merak/ 放入口；engine/、protocol/ 是公开包；其他都在 internal/。开始时少分包。
  3. 文件名后缀：_linux.go、_darwin.go、_windows.go 只在对应系统编译；_test.go 是测试；testdata/ 放样例。沙箱按系统分文件。
  4. 不用 cgo，CGO_ENABLED=0 一台机器编出 6 个平台。go test -race 只在 Linux CI 上跑。
  5. 标准库优先。第三方依赖只有五个：modernc.org/sqlite（命令行宿主）、anthropic-sdk-go（Anthropic 客户端，类型不出 model/anthropic 包，S12 才加）、creack/pty（终端面板的伪终端，纯 Go，只在 Unix 编译；Windows 用 golang.org/x/sys/windows 直接调 ConPTY，见 D4。它们替代 v0.3.1 的 node-pty 原生模块和它的补丁）、zalando/go-keyring（云端令牌，阶段 5 核实是否需要 cgo）、github.com/ledongthuc/pdf（S12 PDF 抽文字；只允许独立抽取包引用，兼容客户端与 read_file 共用，限制输入、解压后内容、页数和累计文字大小）。
  6. gofmt 格式化；pnpm --dir merak typecheck 跑 gofmt 检查和三个系统的 go vet。
  7. 测试写成表格形式，临时目录用 t.TempDir()，不用 mock。注释和 t.Run 标题用英文，check:comments 检查 Go 文件。
  8. 引擎不输出给人看的文字，只输出错误码和事件，由客户端渲染。命令行自带 zh、en 文案表。
  9. 日志用标准库 log/slog，经 platform/log 配置；不用 fmt.Print 做诊断输出。

// Package merak holds what the whole merak program shares: the product version.
package merak

import (
	_ "embed"
	"encoding/json"
)

// manifest is the package.json next to this file. The version lives there so that pnpm release:version sets it for
// every package at once.
//
//go:embed package.json
var manifest []byte

// Version returns the product version from package.json.
func Version() string {
	var pkg struct {
		Version string `json:"version"`
	}
	if err := json.Unmarshal(manifest, &pkg); err != nil {
		panic(err)
	}
	return pkg.Version
}

/**
 * The Go module's typecheck: gofmt, then go vet once per target system without cgo, so code that only builds on one
 * system fails on every machine.
 *
 * Usage (in merak): pnpm typecheck
 */
import { spawnSync } from "node:child_process"

const SYSTEMS = ["linux", "darwin", "windows"]

function run(command: string, args: string[], env: Record<string, string> = {}) {
  const result = spawnSync(command, args, { encoding: "utf8", env: { ...process.env, ...env } })
  if (result.error) throw result.error
  if (result.status !== 0) {
    process.stderr.write(result.stdout + result.stderr)
    process.exit(result.status ?? 1)
  }
  return result.stdout
}

/**
 * Comments and t.Run titles in Go. Interpreted strings, raw strings and runes are skipped whole, so `//` inside one
 * starts no comment.
 */
function goIssues(text: string): Issue[] {
  const starts = [0, ...[...text.matchAll(/\n/g)].map((match) => match.index! + 1)]
  const line = (offset: number) => starts.findLastIndex((start) => start <= offset) + 1
  const end = (from: number, close: string) => {
    const at = text.indexOf(close, from)
    return at < 0 ? text.length : at + close.length
  }
  const comments: { start: number; text: string }[] = []
  const literals: { start: number; text: string }[] = []
  let i = 0
  while (i < text.length) {
    const pair = text.slice(i, i + 2)
    const quote = text[i]!
    if (pair === "//" || pair === "/*") {
      const stop = pair === "//" ? end(i, "\n") : end(i + 2, "*/")
      comments.push({ start: i, text: text.slice(i, stop) })
      i = stop
    } else if (quote === "`") {
      const stop = end(i + 1, "`")
      literals.push({ start: i, text: text.slice(i, stop) })
      i = stop
    } else if (quote === '"' || quote === "'") {
      let stop = i + 1
      while (stop < text.length && text[stop] !== quote && text[stop] !== "\n") stop += text[stop] === "\\" ? 2 : 1
      literals.push({ start: i, text: text.slice(i, stop + 1) })
      i = stop + 1
    } else i++
  }
  const allowed = new Set(
    comments
      .filter((comment) => comment.text.includes("i18n-allow"))
      .map((comment) => line(comment.start + comment.text.trimEnd().length - 1) + 1),
  )
  const found = new Map<number, Issue>()
  for (const literal of literals) {
    const at = line(literal.start)
    if (CJK.test(literal.text) && /\bt\.Run\(\s*$/.test(text.slice(starts[at - 1]!, literal.start)))
      found.set(at, { line: at, kind: "test", text: literal.text })
  }
  for (const comment of comments) {
    const at = line(comment.start)
    if (CJK.test(comment.text) && !found.has(at))
      found.set(at, { line: at, kind: "comment", text: comment.text.replace(/^\/[/*]|\*\/$/g, "").trim() })
  }
  return [...found.values()].filter((issue) => !allowed.has(issue.line)).sort((a, b) => a.line - b.line)
}

// Sink receives every published event before any subscriber sees it. The storage host satisfies it through
// store.Store, so the bus does not import store and the dependency stays one-way.
type Sink interface {
	Append(ctx context.Context, events []Event) error
}

// Bus assigns sequence numbers per stream, persists through the sink, then fans out to subscribers.
// Invariants: Publish returns only after the sink accepted the event; stored events of one stream have consecutive
// Seq starting at 1; subscribers see stored events in Seq order; a subscriber that falls behind gets one Lagged and
// must re-read from the store.
//
// Transient events (the types in Transient; today only message.delta) are the one exception: they get an ID and a
// Time but no Seq, never reach the sink, and are delivered to subscribers in publish order between the stored events
// around them. Dropping them on Lagged loses nothing, because message.completed carries the full text.
type Bus struct { /* sink, clock, id generator, per-stream next Seq, subscribers, mutex */ }

func NewBus(sink Sink, now func() time.Time, newID func() ID) *Bus

// Publish fills ID and Time, and for non-transient types also Seq, persists and delivers.
func (b *Bus) Publish(ctx context.Context, e Event) (Event, error)

// Subscribe returns a channel of matching events and an unsubscribe function. The buffer is bounded (1024).
func (b *Bus) Subscribe(f Filter) (<-chan Event, func())

// Filter matches when every non-empty field matches.
type Filter struct {
	Streams []Stream
	Types   []Type
	Scope   Scope
}

4.2 store：存储契约

引擎向宿主提出的七类请求，分两组：四个管事件（追加、按流读、按归属查、按 id 取），三个管文档（存、取、列）。宿主只认事件的公共字段，不懂业务；要建哪些索引写死在接口说明里，三种宿主照着做。

engine/store/store.go

// Package store is the engine's only view of persistence: the seven requests the engine makes of its storage host.
// Implementations keep what they are given and answer the queries below; they never interpret payloads. Real
// implementations live outside the engine (internal/server forwards each call to the connected host over the
// protocol); store/memory keeps everything in RAM for tests.
package store

type Store interface {
	// Append writes events in order. Within one stream Seq must be consecutive; the store rejects gaps and repeats.
	Append(ctx context.Context, events []event.Event) error
	// Read returns events of one stream with Seq >= from, at most limit, in Seq order.
	Read(ctx context.Context, stream event.Stream, from uint64, limit int) ([]event.Event, error)
	// Find answers index lookups: every event of a task, every task.reported of a group since a time, ...
	Find(ctx context.Context, q Query) ([]event.Event, error)
	// Get returns one event by ID.
	Get(ctx context.Context, id event.ID) (event.Event, error)
	// Put stores a document: a session snapshot, a memory note, a shared document, the group state, a spilled blob.
	Put(ctx context.Context, doc Doc) error
	Fetch(ctx context.Context, kind, key string) (Doc, error)
	List(ctx context.Context, kind, prefix string) ([]DocMeta, error)
}

// Query is deliberately small: a storage host indexes exactly these fields and nothing else.
type Query struct {
	Scope  event.Scope  // every non-empty field must match
	Types  []event.Type // empty means any type
	After  time.Time
	Before time.Time
	Limit  int
}

// Doc is a versioned blob. Rev makes concurrent writers safe: Put fails with ErrConflict when the stored Rev differs
// from doc.Rev, and the caller re-reads and retries.
type Doc struct {
	Kind string            `json:"kind"` // "snapshot", "memory", "document", "state", "profile", "blob"
	Key  string            `json:"key"`
	Rev  uint64            `json:"rev"`
	Body []byte            `json:"body"`
	Meta map[string]string `json:"meta,omitempty"` // title, content type, owner, size ...
}

var (
	ErrNotFound = errors.New("store: not found")
	ErrConflict = errors.New("store: revision conflict")
)

// Buffered wraps any Store for the time the host is away: Append queues in memory up to Limit, reads fail with
// ErrUnavailable, and Reconnect replays the queue in order. Beyond Limit the engine pauses new turns.
type Buffered struct { /* inner, queue, Limit = 4096 */ }
宿主必须建的索引 用途
(stream, seq)，唯一 按顺序重放一条会话或一个群
id，唯一 按事件 id 取细节
(scope.group, time)、(scope.task, time)、(scope.session, seq) 按群、任务、会话检索
(type, time) 按类型扫，比如一个群的所有报告
(kind, key)，唯一 存取文档

Kind = "blob" 的文档是工具的超大输出和产物文件，宿主可以存成单独文件，对引擎仍是一份文档。

4.3 model：通用消息、流式输出、八家服务商、模型目录

这个包把各家模型服务收敛成一个流式接口和一种消息格式，引擎其余部分只认这两样。它还提供按剧本回答的假模型，所有测试用它跑。

Part 和 Chunk

Part 是一条完整消息的组成部分：文字、思考、工具调用、工具结果、图片、文档。一条消息是若干 Part 的有序列表，会话历史里存的是 Part。Chunk 是流式输出时的一小块增量：一小段文字、一小段思考、工具调用的开始或参数片段、用量、停止原因。Chunk 只存在于一次模型请求的过程中，由 Collector 折叠成 Part。界面边生成边显示看的是 Chunk（经 message.delta），历史和下一次请求用的是 Part。

按需加载：工具列表全程不变

基础池的工具带完整 Schema 送给服务商。延迟工具（MCP 服务器的工具、文档解析、很少用的工具）只在系统提示词里占一行名字和一句说明。两个元工具让模型用上它们，而服务商看到的工具列表一个字节都不变，所以任何服务商的缓存前缀都不受影响：

元工具 做什么
load_tools(names) 返回这几个延迟工具的完整 Schema 和用法，作为工具结果进历史（追加，不改前缀）。引擎记下“这条会话已加载了哪些”
call_tool(name, input) 调用一个已加载的延迟工具。S6 直接转交给目标工具的 Run，由工具解码并校验 input，错误与直接调用一致。调用沿用目标工具的权限门。没加载过的工具返回“先 load_tools”。S6 不引入通用 JSON Schema 校验器；接入外部工具时按具体用例再判断。

Anthropic 原生的延迟加载以后可以作为同一机制的加速（同样不改前缀），但不是必需的；第一版只有这一套，六家服务商行为一致。

模型主动发起的动作做成工具；引擎替模型做的内务不做成工具。做成工具：读写文件、跑命令、问人、交报告、汇报进度、写记忆、建任务派任务，类型化参数让引擎能拦截、审批、渲染、审计、并行。不做成工具：上下文压缩、记忆自动召回、工具输出截断、权限判断、沙箱。submit_report 做成工具而不是让模型输出 JSON，因为参数有 Schema 可校验、不合格可退回。模式切换（比如“只规划不动手”）不做成工具，用档案和工具池控制。

工具池

worker.readonly 读文件、列目录、grep、glob、web_fetch。给只许看不许改的成员和子智能体

4.7 loop：agent 循环

请求模型，模型要调工具就执行，把结果交回去再请求，直到模型给出最终回答。它不知道自己是 Leader 还是 Worker，差别全在传进来的工具池、提示词和插话来源。

engine/loop/loop.go

// Package loop runs one turn: ask the model, run the tools it asked for, repeat until it answers.
package loop

type Loop struct {
	Model  model.Provider
	Tools  *tool.Pool
	Window *window.Builder
	Bus    *event.Bus
	Limits Limits // MaxSteps, MaxTokens per turn, wall clock
}

// Input starts a turn or steers a running one.
type Input struct {
	Parts []model.Part
	Actor event.Actor
	Cause event.ID // the event that triggered this input, e.g. human.said or child.finished
}

// Steer feeds a running turn. Poll is read between steps and its inputs become the next user message; Preempt
// cancels the model call in flight so the step restarts with the new input. Workers get a Steer from their runner
// (Leader follow-ups, child results); Leader threads get it from the scheduler.
type Steer interface {
	Poll() []Input
	Preempt() <-chan struct{}
}

type Outcome struct {
	Stop  StopReason // answered, maxSteps, cancelled, failed, refused
	Final []model.Part
	Usage model.Usage
}

func (l *Loop) RunTurn(ctx context.Context, s *session.State, in Input, steer Steer) (Outcome, error) {
	turn := l.begin(ctx, s, in) // emits turn.started and message.sent
	for step := 0; step < l.Limits.MaxSteps; step++ {
		req, err := l.Window.Build(ctx, s) // rebuilds first when over the threshold (section 4.9)
		if err != nil {
			return l.fail(ctx, s, turn, err)
		}
		reply, err := l.ask(withPreempt(ctx, steer), s, req) // streams message.delta, ends with message.completed
		if errors.Is(err, errPreempted) {
			l.inject(ctx, s, steer.Poll()) // emits turn.preempted; the new input is the next user message
			continue
		}
		if err != nil {
			return l.fail(ctx, s, turn, err)
		}
		calls := reply.ToolCalls()
		if len(calls) == 0 {
			return l.finish(ctx, s, turn, reply)
		}
		// Read tools run in parallel, the rest in order. Every result is cut to size by the tool layer before it is
		// appended, and all results of one step go back in a single message.
		l.runTools(ctx, s, calls)
		if steer != nil {
			l.inject(ctx, s, steer.Poll())
		}
	}
	return l.finish(ctx, s, turn, nil) // Stop = maxSteps; the caller decides whether to continue
}
  • 被打断的那次模型调用已花掉的 token 照样记账，已吐出的文字作为一条标了“被打断”的消息留在事件流里。
  • 一步里的多个工具结果合成一条消息送回。Limits 来自档案预算，超了就停，由调用方决定继续还是放弃：单聊里是人，群里是任务的 Leader（怎么继续见 10.2 节“超预算”）。
  • 后台子智能体完成时，运行器把 child.finished 变成一条 Input 经 Poll 送进来，所以父会话不需要轮询。

4.9 window：上下文窗口管理

让会话装得进模型的上下文窗口，同时平时省 token、压缩时不丢关键信息、缓存命中率高。

三条总原则

  1. 入史前截断。大东西在进入历史之前就截断并落盘，历史里只留头尾和引用。
  2. 历史只追加。进了历史的消息、会话开始时的系统提示词和工具列表都不再原地修改。要改变模型看到的东西，只能追加新消息。
  3. 到阈值整体重建。估算超过阈值时，在回合边界把最老的一段换成一条结构化摘要，保留近几轮原文（去掉思考块），然后继续追加。

两个原因。缓存：服务商的提示词缓存是前缀匹配，改动历史里任何一个字节，从那里往后全部失效；只追加的历史每次只多付新增部分。硬性规则：Anthropic 的 Claude 5 系列要求思考块只在产生它的那段对话里有效，新账号默认强制检查，系统提示词、工具列表或更早的消息被改过再传回思考块就是 400 错误；允许的做法正是追加、服务端压缩、或客户端“摘要加去掉思考块的近期原文”。

engine/window/window.go

// Package window fits a session into the model's context window without ever editing history in place, and builds
// the opening packet of a claim session. It is named window instead of context to stay clear of the standard library.
package window

type Budget struct {
	Window    int     // model context size, from the catalog
	Reserve   int     // kept free for the reply: max(model max output / 4, 8k)
	Trigger   float64 // rebuild when the estimate passes this share of Window; 0.9
	Target    float64 // rebuild until the estimate is at or below this share; 0.6
	KeepTurns int     // newest turns kept verbatim (thinking stripped) by a rebuild; 4
	ResultCap int     // tool result size admitted into history, in bytes; 50 KB or 2000 lines, head and tail kept
}

type Builder struct {
	Budget    Budget
	Counter   Counter    // token estimate: a cheap heuristic calibrated per model by the usage providers report
	Summarize Summarizer // one model call with a fixed template; reuses the parent's system and tools for cache hits
}

// Build returns the next request. Steps, in order:
//  1. Estimate system + tools + messages + the pending input.
//  2. If the pending input alone exceeds Window - Reserve: return an error with a code. Never drop it silently.
//  3. If the estimate exceeds Trigger * Window: Rebuild, then re-estimate.
//  4. Emit session.budget with the per-part estimate, then return the request.
func (b *Builder) Build(ctx context.Context, s *session.State) (model.Request, error)

// Rebuild replaces Messages[0:i) with one summary message, where i is the smallest index that brings the estimate
// under Target while keeping at least KeepTurns turns. The kept turns lose their Reasoning parts. The previous
// summary, if any, is an input to the new one. Emits session.rebuilt with the replaced range and the summary's id.
// Runs synchronously at a turn boundary, never in the middle of a tool round.
func (b *Builder) Rebuild(ctx context.Context, s *session.State) error

摘要模板分节，每节一个标题，模型照着填：

# Summary of earlier work (replaces messages 1-212)
## Goal                      what the user asked for, in their words
## Constraints (verbatim)    rules the user stated; copy them exactly
## Decisions                 what was decided and why
## Files touched             paths, one per line
## Current state             what works, what is half done
## Open questions            what still needs an answer
## References                ids worth keeping: mrk://event/..., mrk://blob/..., mrk://doc/...
## Earlier                   one line per earlier summary, oldest first
机制 做法
阈值与上下界 上界 Trigger 90%，超过就重建；重建目标 Target 60%，一次腾够空间，避免刚压完又压；无论如何保留最近 KeepTurns 轮原文。两个阈值之间是迟滞区
工具输出太长 先落盘再截断：工具层把完整输出经 Env.Spill 存成 blob 文档，拿到 mrk://blob/... 引用；历史里只放头尾加一句“完整输出 N 行，用 lookup 带行号范围读取”。bash 的输出额外过一遍噪音过滤（包管理器进度条、重复日志行）
工具输入太长 工具输入进了历史就改不了，靠两头控制：提示词要求大文件分段写；write_file 对超过 N 行的输入返回警告；用服务商的工具参数流式边生成边传
近 N 轮不压缩 KeepTurns：重建保留最近 N 轮的全部原文，只去掉思考块
很老的内容 上一份摘要是新摘要的输入，新摘要对更早的内容只保留 Earlier 一节里的一行。原文都在事件流里，按 id 可取
局部压缩 Rebuild 选的 i 就是局部：只压最老的一段，压到够为止。不做“挖掉中间一段”，那是原地修改历史
工具池按需加载 4.4 节的 load_tools 和 call_tool：服务商看到的工具列表全程不变，延迟工具的 Schema 以工具结果的形式追加进历史
摘要不丢关键信息 固定模板；“Constraints (verbatim)”一节要求逐字保留用户的约束；摘要由单独一次模型调用生成，复用父会话的系统提示词和工具列表（也命中缓存），可用更便宜的模型。失败时不重建，发带错误码的事件，下一步再试
缓存命中 稳定的在前：工具、系统提示词、历史。系统提示词里没有日期和任何每次会变的东西。Anthropic：系统提示词末尾放显式缓存断点，对话尾部用自动缓存；TTL 先用默认 5 分钟。每次请求发 session.budget，记各部分估算和服务商报回的缓存读写量

Leader 线程的会话有个特点：群状态本身就是一份压缩过的摘要，每批事件的摘要消息里都带着它的最新渲染，所以它比 Worker 更快到阈值，但重建更便宜，几乎就是“最新群状态加上和人的对话要点”。set_phase（6.5 节）会主动触发一次重建。

5.3 内置 Worker 运行器和子智能体

worker/builtin 接到认领后新建一条会话，工具池用“执行工具池加群工具”，把材料包渲染成第一条输入，跑 agent 循环。结束的三种情况：模型调用了 submit_report 且报告通过校验；回合结束没交报告，追加一句“请提交报告”再跑一个回合，还是没有就从最后一段回答合成一份并标“合成的”；预算用完或被取消，合成一份结论为“受阻”的报告。单聊用的也是它，只是没有任务卡和群工具。

子智能体和 Worker统一运行器和会话，不统一任务和合并：

  • spawn 就是一个 Runner.Start，用只读或执行档案开一条临时会话，在后台跑；父会话立刻拿到子 id 继续干活。
  • 子智能体完成时发 child.finished，运行器把它变成一条追加消息经 Steer.Poll 送进父会话；wait_child 用于父会话必须等结果的场合。
  • 子智能体没有自己的工作区，在父会话的目录里干活，默认只读池；权限继承父会话已给过的授权，不单独问人。
  • 子智能体不是成员，不能认领任务。它没有 member id，任务池的 Assign 只接受群成员；Leader 的 assign_task 也只能派给成员。Leader 和 Worker 自己开的子智能体都遵守这一条。

5.5 远程的 MerakCode 成员

worker/remote 用 Go 协议客户端连到另一台电脑的 merak serve，对方名下所有已注册成员（内置 Worker、它那台机器上的 Claude Code、Codex 等）都可以被拉进本群当 Worker，事件原样转发。局域网里手动填地址和令牌直连；跨网经云端的设备链接（第 13 节）。

  • 只当 Worker。Leader 线程是群宿主引擎里的调度器、群状态和快速通道，本地群的宿主是本机引擎，云端群的是云端。远程成员不能做默认 Leader，也不能做任务的 Leader，这两种请求被拒。要让编排跑在别处，建云端群。
  • 在对方的检出里干活。对方成员注册时声明了本机检出（远端地址到路径，13.2 节）；群的项目是有远端的仓库且对方声明了同一远端时，远程成员能接 worktree 形态的任务，否则只能接 none。folder 和 inplace 不派给远程成员，派了被拒，错误码回到 Leader。工作区由对方引擎建：先 fetch，再从任务卡的 Base 建 worktree；fetch 后仍拿不到 Base，认领失败。
  • 代码经仓库远端回来。request_merge 时对方把分支 merak/<task>/<member> 推到远端；本机 fetch 这条分支，之后和本地认领一样：审核看的 diff 从本机检出算，合并队列在本机变基、跑检查命令、快进。没有额外的校验步骤，合并队列和人的审核就是校验。合并成功后本机删掉远端上的这条分支，对方释放 worktree。
  • 权限门和沙箱在对方引擎里，按对方成员的档案和对方设备的用户配置（DeniedHosts 是对方设备主人的否决权，10.3 节）；审批请求转到本群，按 10.2 节路由，回答送回对方。
  • 报告、进度、问题、会话事件原样转发进本群的流；对方断线时它名下进行中的认领标为中断，任务线程决定等还是改派。

5.6 外部产品怎么当 Leader

Leader 比 Worker 多的只有一套编排工具和一份群状态，把这两样递给外部产品即可。一条线程一个外部 Leader 进程。

  1. 编排工具经 MCP 暴露。merak mcp --thread T --as leader 启动一个 MCP 服务（stdio），把 6.5 节的编排工具原样暴露，外加 approve 用来回答路由给 Leader 的审批请求。工具调用进入引擎后走和内置 Leader 相同的代码路径，权限、事件、群状态一个都不少。
  2. 队长提示词由 MerakCode 给：prompt/templates/leader.md，和内置 Leader 同一份，加上群简介和线程的任务卡，作为第一条消息发给它。

6.1 线程：群线程和任务线程

Leader 的工作以线程为单位。一条线程是一条很长的 Leader 会话加一个调度器。两种线程：

线程 谁跑 管什么 不管什么
群线程 群的默认 Leader 没有任务归属的事：人在群里随口说的话、新建的顶层任务该不该拆成几个目标、成员进出、不落在任何任务范围里的环境变化、人没指定时给顶层任务挑 Leader 任何已有 Leader 的任务的内部事务
任务线程 这个顶层任务的 Leader 这个任务的全部：拆子任务、派工、收报告、判断合格与否、推进工作周期、回答它的 Worker 的问题、代批常规审批、在任务讨论串里回复人、写这个任务的计划文档、任务完成后向发起人交总结 别的任务；群设置和成员管理

事件按 Scope.Task 的顶层祖先路由到任务线程，没有任务归属的进群线程。一个 Leader 成员可以同时跑多条线程，每条线程有自己的会话；线程之间并发，线程内一次只跑一个回合。顶层任务换 Leader 时（admin 或 owner 调 task.update），旧线程交出一段交接摘要（thread.handed_over），新线程用任务卡、群状态和这段摘要开始。

Leader 不做四件事：不改代码、不跑命令（可以只读地看代码）；不持有 Worker 的全部过程，只持有报告和群状态；不替人做需要人决定的事；不直接合并代码，只向合并队列发请求。

6.2 调度器：全双工的通道，单线程的推理

传统 agent 循环是半双工的：模型调一个耗时工具，工具不返回循环就不往下走，期间来的消息只能排队，智能体一开始干活就“聋了”。全双工的含义是操作进行中仍然有响应：耗时操作立刻返回、结果以后作为事件送回，新输入在下一个推理边界被处理。它不是说模型能打断自己正在生成的每个 token，也不是同时推理无限多件事。

Leader 的每个回合都很短：派任务是调一下 assign_task 立刻返回，Worker 几分钟后的报告是一条新事件；问人是发出问题、回合结束，答案是以后的事件。所以 Leader 不会卡在一个几分钟的回合里。模型调用进行中时新事件怎么办，分三层：

  1. 步与步之间插进去。每步结束时调度器把新到的事件作为下一步的输入追加进去（loop.Steer.Poll）。等待时间就是当前这一步剩下的几秒。
  2. 紧急的打断当前这一步。人的发言、人建或取消任务触发 Preempt：取消正在进行的模型调用，带着新输入重来。只有人的动作有这个待遇。
  3. 代码层先回应。人说话的那一刻引擎立刻发一条 notice.sent 回执；明确有执行方的事直接走快速通道。

结论：通道是全双工的，推理在一条线程内是单线程的。同一条线程里同一时刻只有一个回合在跑；不同线程并发。不在一条线程里并发跑多个回合，因为并发回合看到的是同一份状态的两个快照，会把同一任务派给两个人或互相关掉对方正在处理的任务，输出合并回同一条会话后历史也会错位。线程按顶层任务切分，天然不打架：每条线程只动自己任务子树的状态，群级别的变化只在群线程里发生。

// Priority orders the Leader's queue. Higher runs first; at or above the preempt level it interrupts the step in flight.
type Priority int

const (
	PriorityLow    Priority = iota // file.changed, repo.changed, member.status
	PriorityNormal                 // task.progress, a Worker's question, a human message addressed to someone else
	PriorityHigh                   // task.reported, merge.conflicted, a permission routed to the Leader, a task blocked
	PriorityUrgent                 // human.said to the group or the Leader, a task created or cancelled by a human
)

// Scheduler drives one Leader thread. Turns are short and never wait inside: asking a human or a Worker means
// emitting an event and ending the step; the answer arrives through the queue. A human is never queued behind a
// model call. One thread, one Leader session, one turn at a time; the threads of a group run concurrently.
type Scheduler struct {
	thread  *Thread
	queue   *queue         // priority queue fed by Threads.Route from the group stream and every claim session
	fast    *FastLane      // code-level routing (section 6.3) and trigger rules (section 9.2); runs before the model
	loop    *loop.Loop
	session *session.State // the thread's one long session
	state   *State         // group state (section 6.4), shared by every thread of the group
	digest  Digester       // renders a batch into one message: the state focused on this thread, then the events
	limits  Limits
}

type Limits struct {
	Preempt        Priority      // Urgent
	QuietWindow    time.Duration // low-priority events wait this long so a batch forms; 3s
	Coalesce       time.Duration // messages from one human within this window merge into one input; 2s
	MaxBatch       int           // events per digest; the rest wait for the next turn; 30
	TurnsPerMinute TurnLimits    // from group settings; beyond either limit the queue keeps batching and the fast
	                             // lane keeps answering; no event is emitted
}

// TurnLimits caps how often Leader threads wake the model, over a sliding 60 seconds; slots are given first come,
// first served. It is the group setting "turnsPerMinute". A missing field takes its default; a value must be a
// positive integer. A change applies from the next wake.
type TurnLimits struct {
	Thread int `json:"thread"` // each thread of the group; default 6
	Group  int `json:"group"`  // all threads of the group together; default 30
}

func (s *Scheduler) Run(ctx context.Context) error {
	var pending []event.Event // events that need the model; kept across iterations, never dropped
	for {
		// Wait returns as soon as events arrive and drains what is already there. With pending events and no free
		// slot it also returns, empty, at the moment the oldest turn leaves the 60-second window of the thread or
		// the group; with nothing pending it has no deadline.
		arrived, err := s.queue.Wait(ctx, s.wakeAt(pending))
		if err != nil {
			return err
		}
		arrived = s.fast.Handle(ctx, arrived)            // runs even while over the limit: receipts, routing, delivery
		pending = s.coalesce(append(pending, arrived...)) // keep the newest progress per task, merge one human's burst
		if len(pending) == 0 || !s.limits.take(s.thread) {
			continue // nothing needs the model, or no slot in the thread or the group yet: no cost
		}
		var batch []event.Event
		batch, pending = s.split(pending) // MaxBatch events by priority; the rest wait for the next turn
		in := s.digest.Render(batch, s.state)
		if _, err := s.loop.RunTurn(ctx, s.session, in, s); err != nil {
			s.pause(ctx, err) // publishes group.paused for this thread; a human resumes from the client
		}
	}
}

// Digester renders one batch. The output is a single user message shaped like this, so the model sees the state
// first and every event with its id:
//
//	## Group state (rev 418)                 <- State.Render(budget, thread.Key)
//	## New events (7, 2 coalesced)
//	### Task 01JC5… "Add login tests" (running, Codex)
//	- 01JC6A… task.progress: "wrote 3 of 5 cases"
//	- 01JC6B… permission.requested: write outside workspace → waiting for admin
//	### Group
//	- 01JC6C… human.said (Alice): "can we ship by Friday?"
type Digester interface {
	Render(batch []event.Event, state *State) loop.Input
	Inputs(batch []event.Event) []loop.Input
}

// Poll and Preempt make Scheduler a loop.Steer.
func (s *Scheduler) Poll() []loop.Input          { return s.digest.Inputs(s.queue.Drain()) }
func (s *Scheduler) Preempt() <-chan struct{} { return s.queue.Above(s.limits.Preempt) }
防洪规则 做法
合并 同一个人 2 秒内连发的消息合成一条输入；同一任务的多条进度只留最新一条；同一成员的多次状态变化只留最后一次
静默窗口 低优先级事件先等 3 秒攒成一批；高优先级和紧急事件立刻唤醒
批大小 一次摘要最多 30 条事件，按任务分组、每条带 id、按优先级排；多出来的下一个回合处理
限流 一条线程每分钟最多唤醒模型 6 次，一个群的所有线程合计每分钟最多 30 次，两个数都在群设置的 turnsPerMinute 里可改；按滑动的 60 秒算，名额按到达顺序给；超过后事件继续攒着，快速通道继续发回执和路由，不发事件
空闲零成本 没有事件就没有模型调用；快速通道处理掉的事件不唤醒模型

一台电脑一个 merak serve，进程里每个群若干条线程，群之间、线程之间天然并行；一条线程里的多个子任务靠事件上的任务 id 区分，摘要按任务分组，群状态里每个任务一行。

6.3 快速通道与慢速通道

快速通道处理的事有一个共同点：规则能唯一确定该做什么、该给谁。它在唤醒模型之前跑，处理掉的事件以低优先级进 Leader 的队列让它知情，群状态照样更新。

人在某个任务的讨论串里说话（任务卡下的评论、对某条进度的回复，事件带任务 id） 直接送给这个任务当前的认领；没有进行中的认领就记进任务卡，Leader 下次派工时带上
人建任务时指定了执行成员 直接排队、建工作区、启动运行器
Worker 的审批请求 按 10.2 节的路由表送到有对应角色的人的收件箱；仅询问危险行为模式下常规类别先送给任务线程的 Leader（进慢速通道）。超时转为任务受阻
Worker 点名问某个人 送到那个人的收件箱，答案直接送回那个认领
Worker 问 Leader 进它所属任务线程的慢速通道

人在群里说话，没 @ 任何人 发回执，进慢速通道
仓库被改、目录下文件变了 低优先级进慢速通道攒批；落在某个进行中任务范围里的提升到普通优先级并标“可能冲突”

// FastLane handles the events a rule can settle without the model. Handle returns the events that still need the
// model; every handled event is re-queued at PriorityLow so the Leader stays informed through the next digest.
type FastLane struct {
	tasks    *task.Pool
	members  *group.Registry
	router   permission.Router
	triggers []Trigger // section 9.2, from group settings
	notify   func(ctx context.Context, n Notice) error // emits notice.sent
}

func (f *FastLane) Handle(ctx context.Context, batch []event.Event) (rest []event.Event) {
	for _, e := range batch {
		switch {
		case isMention(e):            // human.said with @member
			f.deliverOrAssign(ctx, e)
		case inTaskThread(e):         // human.said inside a task's discussion thread
			f.deliverToClaim(ctx, e)
		case e.Type == permission.Requested:
			f.router.Route(ctx, e)    // section 10.2; auto mode hands routine ones to the thread's Leader first
		case e.Type == workspace.MergeConflicted:
			f.createIntegrationTask(ctx, e)
		case f.matchTrigger(e):
			f.runTrigger(ctx, e)
		default:
			rest = append(rest, e)
			continue
		}
		if e.Type == group.HumanSaid {
			f.notify(ctx, receipt(e)) // "received, handling N things"
		}
		rest = append(rest, demote(e)) // PriorityLow copy for the digest
	}
	return rest
}

6.5 编排工具

所有编排工具都立刻返回：改群状态、发事件，不等任何人。等待发生在调度器里。群线程和任务线程用同一个工具池，引擎按线程限制范围：任务线程只能在自己的任务子树里建、派、关任务；换 Leader 和成员管理只有群线程能做。

工具 做什么
create_task / update_task 写任务卡：标题、描述、验收标准、碰的文件、依赖、工作区形态、要不要人审核、参与者、预算。群线程建的是顶层任务，任务线程建的是自己子树里的子任务。从草稿到发布发 task.opened。给进行中的任务加预算要 owner 批（10.2 节“超预算”）

6.6 工作周期：状态机

工作周期挂在每个顶层任务上；Leader 拆出的子任务不单独有阶段。一个群里几个目标可以各处于不同阶段。

从哪到哪 条件 谁推进
规划 → 实施 任务卡已拆够、依赖清楚；群设置要求“计划先经人确认”时还要人通过 Leader 调 set_phase；需要确认时由人的 task.reviewed 推进
实施 → 集成 所有子任务都交了报告且 Leader 认可 Leader
集成 → 审核 合并队列全部成功、检查命令通过；或产物全部发布 引擎自动
集成 → 实施 合并冲突（建集成任务）或检查失败（原认领返工） 快速通道自动
审核 → 交付 有审核权的人通过。群设置可以关掉人审核，那就自动交付 人
审核 → 实施 人说“做得不对”，意见发给原认领返工 人，附意见
审核 → 规划、实施 → 规划 人说“方向不对”或改了目标，或 Leader 发现任务拆错了 人或 Leader
任何 → 受阻 预算用尽、问题超时没人答、依赖的目标失败 引擎自动，通知 owner
任何 → 取消 owner 或 admin 取消 人

每次换阶段发 phase.changed，任务看板按阶段分列。人的检查点有两个：规划结束时（可选）和审核阶段（默认开）。所有顶层任务都交付后，Leader 用 notify_human(kind=final) 发总结，这条消息和群状态一起存下来就是归档。

7. 任务、认领与工作区

7.1 群是长期的，任务是群里的工作项

  • 群有自己的生命：目标仓库或目录、成员、Leader、共享文档、群记忆、群简介，可以存在几个月。
  • 任务是群里的工作项。人建的是顶层任务（一个目标），Leader 拆出的是子任务。每个顶层任务有自己的工作周期。
  • 任务卡上可以写参与者（哪些成员可以被派、哪些人收通知）和审核人，不写就是全群。
  • 每个顶层任务有一个 Leader：建任务的人指定，不指定就是群的默认 Leader；admin 或 owner 可以中途更换，任务线程随之交接（6.1 节）。子任务跟随顶层任务的 Leader。
  • 加人、加成员、分享成员都在群里做。只有成员能认领任务；子智能体不是成员。

folder 项目是普通目录（文档、PPT、设计稿），或任务产物不是代码。非仓库项目的默认值 在 <project>/.merak/work/<task>-<member>/ 建目录，复制任务卡列出的输入文件。做完经 publish 复制到产物库 <project>/.merak/artifacts/<task>/ 并登记为 blob，人审核后决定放到项目的哪里。两个任务改同一文件靠任务卡范围避免，避不开就串行
inplace 不能或不想隔离：单成员的群、要在真实环境里跑的任务、不认工作目录的外部产品 直接在项目目录干活，持有项目租约：它在跑时，同一项目的其他 inplace 和 folder 认领不能启动，worktree 认领可以。没有合并步骤
none 调研、回答问题、评审一份文档、写一段文字进共享文档 不建目录，文件工具只读项目目录。产物是报告和共享文档

7.5 集成：合并队列、集成任务、产物发布

9.1 事件从哪来：引擎、环境监视器、外部系统

监视器 怎么做 产出

9.3 Leader 的主动意识

规则能确定的事快速通道做；规则确定不了的事，比如“这句话是闲聊还是需求”“这次提交要不要跟进”，才由 Leader 的模型判断：没有任务归属的在群线程，有的在任务线程。线程看到一批事件后有四种反应：回复（say）；建任务并派工（群线程建顶层任务，任务线程建子任务）；问人；不反应，记进群状态的“观察”里。

主动的边界由两样东西划：权限模式和审批路由（Leader 主动建的任务和派的工和人建的一样要过审批）；群设置里的主动程度，passive（只在被问到时反应，环境事件只记录）、normal（默认）、eager（环境事件也积极跟进，比如有人提交了代码就主动检查对进行中任务的影响，必要时让相关认领变基）。

10. 权限与安全

三层叠加：权限模式决定问不问、问谁；沙箱保证就算绕过了权限门也出不了圈；审批按人的角色路由。现有产品默认全部放行，这套机制的目标是在不牺牲自主性的前提下把风险交给明确选择了它的人。

10.1 三档模式

模式是每个成员档案上的字段（单聊里是每次对话的设置），只有 owner 能把群里成员的模式调高。选了仅询问危险行为或全面接管，出了问题由选的人负责，界面明示。

模式 什么要问 什么自动放行 沙箱 谁来答
每次询问 ask（默认） 所有写文件、跑命令、联网、改群状态的调用 只读 开。本机没有可用沙箱时照样逐次询问；不能转发审批的成员改为启动前问一次（10.3 节） 人。群里按角色路由
仅询问危险行为 auto 工作区外的写入、删除、保护路径（.git/hooks、.git/config、MerakCode 配置文件）、新的网络目标、合并到目标分支、超预算、用户规则里标“问”的命令 工作区内的写文件、用户规则里标“允许”的命令、已允许过的网络目标、包管理器缓存目录的写入 开。本机没有可用沙箱时退化为逐次询问；不能转发审批的成员改为启动前问 admin（10.3 节） 常规类别在群里先给任务线程的 Leader 代答（拿不准问人）；需要 admin 或 owner 的直接给人。单聊里直接问人
全面接管 takeover 什么都不问 一切 关。所有操作直接放行 没人。失败的命令不自动重跑，由模型或人决定下一步

所有模式下“记住这个选择”都有效：这次会话、以后都允许；后者写进用户配置。全面接管在沙箱做出来之前（S25）不提供，因为用户要在“有沙箱”和“关沙箱”之间做选择，先得有沙箱。

// Need maps a request to the role that may answer it. It is a table, not a rule language.
func Need(req Request, ws workspace.Workspace, g group.Group) Role {
	switch {
	case req.Spec.Effect == tool.EffectWrite && !ws.Contains(req.Path) || req.Deletes || ws.Protected(req.Path):
		return group.RoleAdmin
	case req.Spec.Effect == tool.EffectNetwork && !g.Settings.AllowedHost(req.Host):
		return group.RoleAdmin
	case req.Kind == KindLaunch: // a member that cannot forward approvals, started without a sandbox (section 10.3)
		return group.RoleAdmin
	case req.Kind == KindWorkspace: // an MCP server from the workspace file (section 10.5)
		return group.RoleAdmin
	case req.Kind == KindMerge && g.Settings.MergeNeedsOwner, req.Kind == KindBudget, req.Kind == KindMode:
		return group.RoleOwner
	default:
		return group.RoleApprover
	}
}

// Route finds who answers. In auto mode in a group, a routine request (a tool call whose Need is RoleApprover, raised
// by a Worker) goes first to the task thread's Leader, even when a human with the role is online; the Leader answers
// with approve or escalates with ask_human. Every other request, and every escalated one, goes to humans in order:
// humans named on the task card with the role and online; any online human of the group with the role; otherwise
// the request waits in the inboxes of everyone with the role (across devices through the cloud). Reviews, plan
// confirmations and requests raised by a Leader thread itself always go to humans. Timeout counts from the first
// request, not from the escalation; when it passes, the task is blocked and the owner is notified. Workspace
// confirmations belong to no task: they have no Timeout and wait in the inboxes until answered. A human with a
// higher role may always answer for a lower one.
func (r *Router) Route(ctx context.Context, req Request) (Answerer, error)

本地单人使用时这个人持有全部角色，所有请求都到他这里；角色检查是真的，只是落在同一个人头上。外部 Leader 用 MCP 的 approve 工具回答，受同一张表限制，想批 admin 或 owner 级别的事会被拒绝并转给人。

超预算

预算有两层：成员档案的预算限制这个成员在一个任务（单聊里是一条会话）上的用量，任务卡的预算限制整个任务所有认领的合计；两层都只能由 owner 放宽。认领撞到任何一层的 token、费用或时长上限就停下并交一份“受阻”报告，任务受阻。任务线程的 Leader 决定下一步：拆细、改派、取消，或者申请加预算。

  • 申请：Leader 调 update_task 给任务卡加预算，写的是增量，token、费用、时长至少一项大于零；步数是每回合的限制，不在此列。非 owner 提出的加预算是一个 Kind 为 budget 的请求，路由给 owner，任务卡在批准前不变；owner 自己经 task.update 改预算直接生效。请求带任务 id、Leader 的一句话理由、已用量（token、费用、已用时长）、现在的上限（任务卡的和受阻成员档案的）和增量。
  • 批准：增量记进任务卡的 Grants，不改档案，不影响别的任务。任务的合计上限是任务卡预算加所有 grant；每个成员在这个任务上的个人上限是它档案的预算加所有 grant；时长上限同样顺延。任务回到受阻前的状态，Leader 重新派工：派回原成员则原会话继续，派给别人按接力规则。
  • 拒绝：任务保持受阻，Leader 拆细、改派或取消；引擎不会自动重新申请。
  • 单聊：没有 owner 审批。turn.finished 带预算类停止原因时客户端提示人；人下一次 session.send 带 extendBudget: true 就给这条会话再加一份档案预算（token、费用、时长各加档案里的数），不带的发送被拒并返回同一个错误码。

10.3 沙箱

权限门是判断，沙箱是强制。每次询问和仅询问危险行为两档下，所有成员进程，包括内置 bash 的子进程、Claude Code、Codex、opencode、pi、ACP 智能体、纯命令行程序，都通过 platform/sandbox.Command 启动，带着这次认领的工作区对应的沙箱配置。全面接管下 Command 直接返回不加限制的进程。

internal/platform/sandbox/sandbox.go

// Package sandbox starts processes with operating-system enforced limits. The same Profile means the same thing on
// all three systems; each has its own file (sandbox_darwin.go, sandbox_linux.go, sandbox_windows.go).
package sandbox

// Profile is plain data so it can be written to a file for helper processes. Every path is absolute and resolved to
// its real location.
type Profile struct {
	ReadDeny   []string // credential directories under the home folder (.ssh, .aws, .azure, .kube, .gnupg, .docker, gcloud, gh), the
	                    // engine's own data directory except the private temp dir, and the state directories of the other products
	WriteAllow []string // the workspace, the engine's private temp dir, package manager caches, the member's own product state
	                    // directory (~/.claude with .claude.json moved inside through CLAUDE_CONFIG_DIR, ~/.codex, ...); nothing else
	Protect    []string // never writable even inside WriteAllow: .git/hooks, .git/config, merakcode.json(c), .merakcode/
	Network    Network  // off, allowlist, or on; allow and deny rules (host, IP, *.domain, optional :port); blocked ports; allowed local ports
	EnvAllow   []string // environment variable names passed through; everything else is stripped
}

// Status reports what this machine enforces for one profile. Available covers the file limits (ReadDeny and
// WriteAllow) and is what the permission policy keys off. Network and Protect are reported on their own, because a
// machine can enforce the files and still not the rest.
type Status struct {
	Available bool         // the file limits are enforced
	Backend   string       // seatbelt, landlock, windows-account, none
	Network   string       // how outbound traffic is forced to the proxy: seatbelt, namespace, account, ports, none
	Limits    []string     // what the mechanism leaves open: loopback-open, own-addresses-open, port-only, udp-open; the clients render them
	Protect   []PathStatus // one per Protect path
	Reason    string       // what is not enforced and why, for the UI
}

type PathStatus struct {
	Path  string
	State string // enforced: the OS refuses writes; unenforced: only the rollback after exit; missing: the path does not exist
}

// Status takes the profile because what can be enforced depends on which paths exist. Windows needs a one-time
// administrator setup (a separate low privilege account); Linux needs Landlock in the kernel; macOS has sandbox-exec.
func (l *Launcher) Status(ctx context.Context, p Profile) Status

// Command returns an exec.Cmd confined to the profile. In takeover mode the launcher is Disabled and returns a plain
// command. When Status is not Available, the permission policy asks for every call instead (section 10.1).
func (l *Launcher) Command(ctx context.Context, p Profile, name string, args ...string) (*exec.Cmd, error)

主机名白名单由引擎的本机代理执行，三个系统的机制只负责把成员的出站流量限制到只能到这个代理。Status.Network 报告用的是哪种机制，Status.Limits 列出这种机制管不到的地方：namespace 和 seatbelt 没有缺口，回环也只放行代理端口和 LocalPorts；account 只封非回环流量，回环和本机自己的地址开着（loopback-open、own-addresses-open），LocalPorts 和 BlockedPorts 不生效；ports 只认端口不认主机，UDP 不管（port-only、udp-open）。只有 none 让策略多问：成员能直连任何地方，主机名白名单形同虚设。其他几种都算网络已强制，缺口在界面的“部分强制”里列出，不多问。

读的范围三个系统一致：用户能读的减去 ReadDeny。外部产品要读写自己的状态目录（Claude Code 的 ~/.claude，.claude.json 经 CLAUDE_CONFIG_DIR 也收在这里、Codex 的 ~/.codex、opencode 的 ~/.config/opencode 和 ~/.local/share/opencode、pi 的 ~/.pi），登录令牌也在里面，所以适配器把自己产品的状态目录加进这次运行的 WriteAllow，把其他产品的加进 ReadDeny。引擎自己的数据目录也在 ReadDeny 里：用户配置里有密钥，存储里有对话；私有临时目录除外。

Landlock 和 NTFS 只能授权已存在的路径，所以 WriteAllow 里的路径在授权前必须存在，而成员进程自己创建不了它们。产品的状态目录由适配器在启动前以用户身份建好（不存在才建，权限只给用户），已有的不改，建不出来算启动失败。产品直接放在用户目录顶层的状态文件没法这样处理：预建文件不行，产品写它时会在旁边排他地建锁文件和临时文件再改名，预建的锁会被当成已占用。办法是用产品自己的配置目录变量把这个文件收进它的状态目录，状态目录不换地方，登录和设置都还在原处：Claude Code 的适配器设 CLAUDE_CONFIG_DIR 指向真实的 ~/.claude（用户自己设了就用用户的），.claude.json 和它的锁、临时文件就都落在这个已可写的目录里；第一次运行时目录里还没有 .claude.json 而 ~/.claude.json 存在，适配器以用户身份复制一份进去，权限只给用户，此后两份各走各的，成员的项目记录和启动计数不会写回用户自己的那份；~/.claude.json 本身永远不授权。不接受“沙箱拒绝后产品退回直接写用户的文件”：几个成员同时跑时没有锁的直接写会损坏用户自己的配置。三个系统都这么做，macOS 虽不需要也保持一致。

系统 机制
macOS sandbox-exec 加一份按 Profile 生成的 Seatbelt 规则，文件、保护路径和网络都由它强制。系统自带
Linux Landlock 强制 ReadDeny 和 WriteAllow，Available 只取决于它。网络靠用户加网络命名空间，开不了时按内核能力降级；保护路径靠挂载命名空间里的只读 bind mount，没有时报未强制
Windows 一组低权限账户，每个活动的认领租一个，加只写限制令牌、NTFS 权限和防火墙规则；第一次需要管理员做一次初始化，引擎启动时验证账户可用，凭据变化后重新探测

Linux

  • Landlock 只有允许规则，父目录的权限向下传给整个子树，所以它只负责 ReadDeny 和 WriteAllow。内核没有 Landlock 时 Available 为假，这是 Linux 上唯一让沙箱不可用的条件；命名空间开不了不算。
  • 网络按能力降级：能开用户加网络命名空间就开，成员只剩回环，助手进程把回环端口桥到引擎的代理，Status.Network 报 namespace；开不了而内核在 6.7 以上，用 Landlock 的网络端口规则只放行代理端口，报 ports，它只认端口不认主机，也不管 UDP，Limits 报 port-only 和 udp-open；两样都没有报 none。
  • 已存在的保护路径在有挂载命名空间时以只读方式 bind mount 到自身，这是在可写目录里精确只读化一条路径的唯一非特权手段；没有挂载命名空间时报未强制。不收回父目录的创建权：对工作区根目录那会禁止新建顶层文件，对 .git 会让 git 写不了锁文件。
  • 不用 seccomp：项目不用 cgo，只能手写 BPF，白名单会打坏 Node、Bun、Rust 写的成员，黑名单能拦的 Landlock 已经限制。

Windows

  • 一次性初始化由管理员完成：建一个本地组和一组沙箱账户（默认 4 个，初始化时可改）加进组，账户不在登录界面显示，凭据存进系统凭据库，每个账户一条防火墙规则封掉非回环的出站。Windows 防火墙不过滤回环，也不过滤发往本机自己地址的流量，所以成员能连到本机上的服务，这是防火墙的形状，不是这台机器的降级：Status.Network 报 account，Limits 报 loopback-open 和 own-addresses-open，不多问。管理员步骤之后以用户身份继续：给组在用户资料目录上授读取和执行并继承（目录属于用户，不需要特权；目录大时第一次要几分钟，界面显示进度），给组在 merak 的安装目录上授读取和执行。引擎启动时验证账户可用，凭据变化后重新探测。
  • 读的范围由此和另外两个系统一样：用户能读的减去 ReadDeny。ReadDeny 靠显式 Deny 读取并继承，离目标最近的继承 Deny 排在更远的继承 Allow 前面，所以压得过用户资料目录上的 Allow。ReadDeny 分两类：全机一致的（凭据目录、引擎数据目录）给组加，租用时补上新出现的目录，不撤销，重置时随组一起清；随成员变的（其他产品的状态目录）给本次账户加，归还时删掉，否则 Claude Code 跑过一次之后 Codex 自己也读不了 ~/.codex。私有临时目录在引擎数据目录下，它的 DACL 断开继承，只给用户、SYSTEM、管理员和租用的账户，引擎目录上的 Deny 不进来。工作区、私有目录和助手文件通常在用户资料目录或盘根目录下，祖先目录都可读；遇到不可读的祖先，租用时给账户加只读加穿越，只作用于该目录不继承，归还时撤销。
  • 隔离的单位是认领，所以每个活动的认领租一个账户，认领内的所有启动共用它，认领结束归还。单聊按会话租：第一次启动成员进程时租；会话空闲（没有在跑的轮次、没有后台命令）后不立即归还，池子不够时才从空闲最久的会话收回，下一轮再租，上次那个账户还空着就优先用它，这样桌面端常年开着的对话不占死账户，也不用每轮在工作区上重打 ACL。账户用完且没有可收回的，新认领排队等待，状态里显示“等待沙箱账户”。不加“结束会话”的协议操作。租用时引擎在 WriteAllow 和私有目录上给这个账户授 Modify，在已存在的保护路径上给它加显式 Deny（WriteAllow 的授权会向下继承到 .git/hooks，这条 Deny 不能省）；归还时删掉这些 ACE，引擎启动时清理上次残留的。
  • 引擎用 CreateProcessWithLogonW 以租用的账户启动 merak 的内部助手子命令；助手用 WRITE_RESTRICTED 创建自己令牌的限制副本，再用 CreateProcessAsUser 在一个 Job 对象里启动成员，Job 关闭即杀，退出码原样转发，标准流靠句柄继承。成员跑在助手新建的未命名窗口站和桌面里，不在用户的交互窗口站上，读不到剪贴板、发不了窗口消息。全程不需要特权。限制 SID 三个：账户自己的 SID、Everyone（S-1-1-0）、WRITE RESTRICTED（S-1-5-33）。写任何对象都要 ACL 同时授权给账户和这三个之一：Authenticated Users 和 Users 的授权不算数，所以盘根下默认对 Authenticated Users 开放写入的目录、ProgramData 都写不了；别的认领的工作区授权给别的账户，也写不了；账户自己的 SID 让它创建的对象照常可用，命名管道的默认 DACL 只给创建者、SYSTEM 和管理员，node 的子进程管道靠这条；Everyone 和 WRITE RESTRICTED 让系统设备（CNG 等）和内核对象命名空间照常可用。读不受影响。不降低完整性级别，不打 Low 标签，不改系统对象的 DACL。
  • 已知的缝：盘根下的目录继承 CREATOR OWNER 完全控制，成员新建的文件因此带着账户的 ACE，认领结束后留在 inplace 工作区里的这些文件，下一次租到同一账户的认领还写得了。worktree 删除时文件随之消失；租账户时优先选最近没在这个项目干过活的。
  • TEMP 和 TMP 改指私有目录；USERPROFILE、APPDATA、LOCALAPPDATA 保持真实路径，成员要读 ~/.gitconfig、~/.npmrc 和产品自己的配置，能写的只有 WriteAllow 里的缓存目录和产品状态目录。工作区的所有者是用户不是沙箱账户，git 会报 dubious ownership，环境里经 GIT_CONFIG_COUNT 加一条 safe.directory=*。写注册表 HKCU 会失败，接受。代理若用命名管道，给租用的账户授写权限，或者直接走回环 TCP。成员在限制令牌下跑不起来，走下文“沙箱不可用时”的启动询问。

保护路径

  • 不存在的保护路径跳过：不报错、不限制父目录、不预建，Status.Protect 记为缺失。配置文件的真正防线在引擎（10.4 节），沙箱只是第二道。
  • 三个系统都加一道回滚：每次启动前给已存在的保护路径拍快照（路径和内容），进程退出后比对，改过的还原、新增的删掉、删掉的放回，动过的文件列进 tool.completed 的错误，界面显示“被沙箱拦下”。回滚不依赖系统机制，所以 Linux 没有挂载命名空间时保护路径仍有一道实际的防线，macOS 和 Windows 上它是系统强制之外的第二道。Status.Protect 的 unenforced 表示“系统不强制，只有回滚”。快照由引擎而非成员进程持有，成员改不了它。

网络白名单从哪来

  • 一次运行的白名单是成员档案的 Network（这个成员自己要连的服务，比如它的模型服务或中转站，5.2 节）并上群设置的 AllowedHosts（这个群批准过的目标）；单聊再并上用户配置里“以后都允许”记下的主机。拒绝列表只有两处：用户配置的 DeniedHosts 对本机上的每次运行都生效，包括群里的，是设备主人的否决权；群设置的 DeniedHosts 由 admin 维护，对群里每次运行生效。一次运行合并两处拒绝列表。档案的 Network 只放允许规则。
  • 一条规则是主机名、IP 或子域通配 *.example.com，可以带 :端口；通配不匹配裸 IP，也不匹配 example.com 自己。单独的 * 只接受在用户配置的 AllowedHosts 里，等于本机单聊的网络模式 on；群里没有 *。拒绝列表优先于允许列表，用于在 on 或宽通配下挖掉个别主机；审批不能覆盖拒绝：命中拒绝列表的目标代理直接拒绝，不发审批，错误里写明是用户配置还是群设置拒的。代理按请求行里的主机判断，不看 Host 头；解析出的地址再查一次回环和保留地址，不能靠域名绕到本机服务。
  • 引擎不替任何产品加默认域名。代理拒绝一个目标时，tool.completed 的错误带被拒的主机名和成员名，错误码的提示指向成员档案的网络列表。桌面端的档案表单可以按产品种类和环境变量里的地址预填建议，引擎不参与。
  • 适配器关掉产品的非必要流量，比如 Claude Code 的遥测和错误上报；否则用户会看到一串域名被拒，然后盲目放行。
  • 群里 admin 加成员时看到并接受档案当时的主机列表，记在群成员记录的 Hosts 里。之后拥有者改档案新增的主机，在这个群里算新的网络目标，问 admin，同意后更新成员记录。改档案仍只有拥有者能做。
  • 代理遇到不在白名单的目标时发起审批并挂住连接，最多等两分钟，超时拒绝，审批请求保持打开；同意后记进群的 AllowedHosts 或单聊的用户配置，成员重试或下次派工就能通。内置工具的联网先过权限门，到不了代理。

沙箱不可用时

  • 能转发审批请求的产品（Claude Code、Codex、opencode、通用 ACP）以“每次都问”的模式启动，所有请求进我们的权限门和路由，用户在 MerakCode 里选的模式对它们同样生效。沙箱不可用时每个非只读调用都问人。
  • 不能转发的产品（pi、纯命令行程序）引擎看不到它们内部的调用，能看到的唯一一次调用是启动，所以启动本身按危险调用询问：单聊问用户，群里直接问 admin，不经 Leader。请求带成员名、Status.Reason 和一句说明：这个成员不能转发审批，本机没有可用沙箱，启动后它的操作不受限制。文件可用而 Status.Network 为 none 时同样启动前问一次，说明改为：网络没有强制，文件仍受限；account 和 ports 不触发这一问。“记住这个选择”有效，按成员加项目记。拒绝则启动失败，记进 tool.completed 的错误，有自己的错误码；群里这条任务回到看板等人改派。全面接管下照旧不问。
  • 不能转发的产品只有沙箱这一道闸，档案里标出；沙箱不可用时成员记录再标 Unconfined，Leader 派敏感任务时避开。
  • 沙箱的拒绝发生在系统调用层。引擎监视 stderr 和退出码，能识别的拒绝记成 tool.completed 里的错误，界面显示“被沙箱拦下”。
  • 沙箱一致性测试在三个系统的 CI 上真跑（3.8 节）。

10.4 安全边界

  • 成员的环境变量值、密钥、令牌不进事件、不进报告、不进日志，只出现变量名。记忆写入、报告提交、给人的通知文字、日志处理器过同一个密钥扫描。
  • 引擎的端口和令牌写在数据目录里一个只有当前用户能读的文件中；WebSocket 校验令牌和 Origin。
  • 界面渲染模型输出的 Markdown 要清洗；严格的 CSP；contextIsolation 开、nodeIntegration 关。权限判断只在引擎里做。
  • 云端群里哪些数据离开本机逐项列清楚并在建群时确认：群的事件（含对话）、报告、产物元数据会上传；文件内容只以路径和行数出现，产物按需上传。
  • 云端登录令牌由引擎存进系统凭据库，界面拿不到；凭据库不可用时存在数据目录里受限的文件中。
  • 工作区配置（merakcode.json、merakcode.jsonc、.merakcode/）来自仓库，可能是克隆来的。引擎在会话开始时读一次并记内容哈希；涉及安全的字段，比如权限规则、MCP 服务器、要跑的命令，首次见到的哈希和之后的任何变化都要人确认才生效，权限判断和 MCP 只读已确认的快照。确认和拒绝按项目以内容哈希记进用户配置，被拒绝的不再重复问。文件格式、确认的单位和记录见 10.5 节。
  • 确认后的配置在它下一次被读取的边界生效，进行中的操作继续用原快照：按轮读取的配置下一轮前生效；工具列表和 MCP 服务器在会话开始时定下，下一次会话生效；沙箱 Profile 和 setup 命令在下一次认领或启动成员进程时生效。

10.5 工作区配置与 MCP 服务器

MCP 服务器有两个来源：用户配置（数据目录里的 merakcode.json）和工作区配置（工作区根目录的 merakcode.json 或 merakcode.jsonc）；merak acp 的会话多一个来源，编辑器传进来的，见下面“ACP 客户端”一条。两处用同一个 mcpServers 字段，同名时用户配置的生效，工作区那一项不启动也不问。用户配置是用户自己写的，不用确认；工作区配置可能是克隆来的，按 10.4 节逐项确认。

}
  • 文件：读会话工作区的根目录，群里是认领的工作区，单聊是会话的工作目录。两个文件用同一个解析器：标准 JSON 加注释和尾逗号，自己写，不加依赖。两个文件同时存在、解析失败或有未知字段时整份不用，发一个 config 域（3xxx）的 MRK 码，会话照常开始。现在只有 mcpServers 一个字段；.merakcode/ 目录留给以后。
  • 字段：服务器名由 1 到 32 个字母、数字、_、- 组成；command 必填，含 / 的相对路径按工作区根解析，否则在 PATH 里找；args 是字符串数组；env 是变量名到字面值，不做 ${VAR} 展开，要密钥的服务器写进用户配置。只支持 stdio，url 这类远程字段现在算未知字段。
  • 确认：单位是一台服务器。哈希是这一项解析后重新编码成 JSON 的 SHA-256，注释、空白、键的顺序和别的服务器都不影响它。请求的 Kind 是 workspace，需要 admin，Leader 批不了；单聊直接问人。请求里有项目、服务器名、command、args 和 env 的变量名，不带变量值。回答一律记进用户配置的 workspaceTrust，按（项目、条目、哈希）一条，旧的不删，来回切分支不会反复问。同一个（项目、条目、哈希）同时只有一个未答的请求。这种请求不挂在任务上，不超时、不让任务受阻，留在收件箱等人回答。
  • 生效：会话第一轮开始前定下这条会话的服务器。已确认的启动，被拒绝的跳过，没确认过的这次不启动，同时发出确认请求；确认后下一次会话生效。项目按 10.3 节取：群里是群的项目目录，单聊是会话的工作目录，都解析成真实路径，所以同一个项目的各个工作树共用确认记录。
  • 进程：服务器经 platform/sandbox.Command 启动，用这条会话的沙箱配置，工作目录是工作区根，环境是 EnvAllow 放行的变量加上 env，联网走同一个代理和白名单；全面接管下不加限制。会话开始时启动并取工具列表，会话结束时停掉。启动或取列表失败（10 秒没完成也算失败）就跳过这台，发一个 tool 域（5xxx）的 MRK 码，会话照常继续。
  • 工具：每个工具成为延迟工具 mcp__服务器名__工具名，在权限门里算 exec，不信服务器自己报的只读标注。
  • 范围：这两处的服务器只给内置成员用。外部产品读它自己的 MCP 配置，MerakCode 只给它挂 merak mcp（8.3 节）。
  • ACP 客户端：merak acp 的 session/new 可以带 mcpServers。客户端是用户自己的编辑器，它替用户回答审批请求，所以它传的服务器按用户配置对待：不确认，这条会话就启动。字段规则同上，只收 stdio；initialize 回的 mcpCapabilities 里 http 和 sse 都是 false，客户端仍传了这两种就拒绝整个 session/new（-32602）；与用户配置同名时用户配置的生效。env 的值按密钥处理。用户配置和工作区的服务器在 ACP 会话里照常生效；工作区的确认请求像别的审批一样以 session/request_permission 发给编辑器，回答记进 workspaceTrust，下一次 session/new 生效。
  • 用户配置里 env 的值按密钥处理：config.get 只给变量名，诊断包脱敏。config.set 暂不支持这个字段，用户手改文件。

11. 协议与 SDK

11.1 传输方式和握手

存算分离要求引擎能反过来请求客户端，连接必须是双向的。协议用 JSON-RPC 2.0，跑在 127.0.0.1 随机端口的 WebSocket 上，令牌放在连接头里，校验 Origin。连上以后第一条消息必须是 hello。 

→ {"jsonrpc":"2.0","id":1,"method":"hello","params":{
     "protocol":1,
     "client":{"name":"desktop","version":"1.0.0"},
     "capabilities":{"store":true,"terminal":true,"approve":true}}}

← {"jsonrpc":"2.0","id":1,"result":{
     "protocol":1,"engine":"1.0.0","device":"01J...",
     "store":"accepted"}}          // or "declined": another host is connected

协议版本对不上时引擎回错误并断开，错误码提示升级。approve 表示这个客户端能替用户回答审批和问题。终端的字节流走单独的 WebSocket 二进制帧。

11.3 存储宿主要遵守什么

  • 同一时刻只有一个宿主。第二个声明的收到“拒绝”，仍可作普通客户端。
  • store.append 返回代表已写盘。引擎在它返回前不分发事件。宿主应批量写，一次请求可带多条事件。
  • 宿主只给公共字段建索引，正文是不透明 JSON。公共字段的变化走协议版本，宿主不需要迁移逻辑。
  • 宿主断开后引擎切到缓冲模式；重连后先补写缓冲，再恢复。缓冲超上限时引擎暂停新回合并发 engine.storage。
  • 三种宿主用同一份存储格式说明和同一套一致性测试（第 12 节）。

11.4 类型只写一遍

每种事件的正文类型由发出它的包在 init 里向 event.Register 登记，生成器据此产出按事件类型区分的 TypeScript 联合类型。JSON Schema 生成器自己写：协议类型里没有泛型和接口字段，基于反射几百行够用。

12. 存储宿主与产品形态

12.1 三种宿主，一份存储格式

产品形态 存储宿主在哪 格式
桌面端 Electron 主进程里 SDK 的 SqliteStore 数据目录里的 SQLite 文件 merak.db，加 blobs/ 目录放大文件
命令行 Go 客户端层的 internal/localstore，没有桌面端时由 merak serve 自己挂上 同一个文件、同一个 schema。桌面端和命令行共用一个数据目录，谁先启动引擎谁当宿主

“同一份格式”落实为三样东西：

  1. schema/store.sql：一份建表语句，事件表、文档表、索引，对应 4.2 节的索引表。Go 的 localstore 和 TypeScript 的 SqliteStore 嵌入同一个文件执行。
  2. 一套一致性测试：Go 版和 TypeScript 版测同样的行为，加一组黄金数据库文件，Go 宿主写出的 merak.db TypeScript 宿主必须能原样读出，反之亦然。
  3. 数据目录布局：<data>/merak.db、<data>/blobs/<hash>、<data>/engine.json（端口、令牌、进程 id，只有当前用户可读）。默认位置按系统惯例：macOS ~/Library/Application Support/MerakCode，Windows %APPDATA%\MerakCode，Linux ~/.local/share/merakcode。

schema/store.sql（骨架）

-- One schema for every SQLite host; the cloud maps the same tables onto PostgreSQL.
CREATE TABLE events (
  id      TEXT PRIMARY KEY,          -- ULID
  stream  TEXT NOT NULL,             -- "session:<id>" or "group:<id>"
  seq     INTEGER NOT NULL,          -- consecutive per stream, starts at 1
  time    TEXT NOT NULL,             -- RFC 3339 UTC
  type    TEXT NOT NULL,
  grp     TEXT, task TEXT, session TEXT, turn TEXT,   -- scope, nullable
  actor_kind TEXT NOT NULL, actor_id TEXT,
  cause   TEXT,
  payload BLOB NOT NULL,             -- opaque JSON
  UNIQUE (stream, seq)
);
CREATE INDEX events_group_time   ON events (grp, time);
CREATE INDEX events_task_time    ON events (task, time);
CREATE INDEX events_session_seq  ON events (session, seq);
CREATE INDEX events_type_time    ON events (type, time);

CREATE TABLE docs (
  kind TEXT NOT NULL, key TEXT NOT NULL, rev INTEGER NOT NULL,
  body BLOB NOT NULL,                -- large blobs may live in blobs/<hash> with body holding the hash
  meta TEXT,                         -- JSON object
  PRIMARY KEY (kind, key)
);

选 SQLite 而不是 JSONL：按群、任务、时间的查询需要索引；SQLite 一个文件、带索引、事务安全，两种语言都有不需要 cgo 的实现。Go 侧用 modernc.org/sqlite（纯 Go）。

12.2 桌面端宿主

SqliteStore 用 Node 自带的 node:sqlite，不加 npm 依赖；实现前在 Electron 44 里核实 process.versions.node 含稳定版，不含则退回 better-sqlite3。主进程在 hello 里声明 store: true；关窗口进托盘时继续当宿主；彻底退出时先等引擎优雅退出再关库。

13.1 设备链接

// Package cloud is the only place the local engine talks to the cloud service. Without an account it is Null.
package cloud

type Link interface {
	// Connect opens the outbound connection and keeps it alive with reconnects; it returns when ctx ends.
	Connect(ctx context.Context, creds Credentials) error
	// Announce tells the cloud which members this device offers, with their profiles' summaries and status.
	Announce(ctx context.Context, members []group.Member) error
	// Forward sends a client's request about a cloud group upward unchanged: group.create with kind cloud,
	// group.say, task.create, permission.reply ... The cloud is the host and answers.
	Forward(ctx context.Context, method string, params json.RawMessage) (json.RawMessage, error)
	// Inbound delivers what the cloud sends to this device.
	Inbound() <-chan Inbound
	// Publish forwards events this device produced in cloud groups (claim sessions, local tool runs) upward.
	Publish(ctx context.Context, events []event.Event) error
}

type Inbound struct {
	Assignment *worker.Assignment // start a run on a local member
	Message    *loop.Input        // steer a running one
	Cancel     *event.ID          // cancel a claim
	Reply      *permission.Reply  // a human answered through the cloud
	Notice     *leader.Notice     // for this device's user: approvals, questions, mentions
	Events     []event.Event      // cloud group events this device subscribes to, for display
	ToolCall   *tool.Call         // a cloud Leader's read-only code tool to run on this device's checkout
}

// Null is used when no account is configured. Every method returns ErrNoCloud.
type Null struct{}

  • 云端服务是单独仓库里的单独 Go 程序 merak-cloud，引用本仓库的公开包 engine/（Leader 线程、任务池、群状态）和 protocol/（设备链接的消息类型），按提交的伪版本引用。

15. 实施路线：5 个阶段、32 个引擎切片和 10 个桌面端切片

每个切片从入口（命令行或协议）一直切到引擎底层，做完就多一个用户看得见的能力。切片内部按 TDD 推进：一次只写一个会失败的测试，让它通过，再写下一个，不把一个切片的测试全写完再写实现。每个切片列的是“按顺序逐个实现的行为”，每一行是一轮红、绿、整理。

  • 一个切片一份施工单，格式照 3.9 节，一次提交或一个很短的分支。切片之间按顺序做。
  • 每个切片只加“只实现”里列的东西。第 4 到 10 节的代码是最终形状，不是当前切片的清单。
  • 切片完成标准：列出的行为全部有测试且通过，go test ./... 和 pnpm check 通过，CI 全绿，用户能感知的改动在 CHANGELOG.md 里有中英各一行，第 17 节清单对过一遍。
  • 阶段之间停下来用一段时间，再调整后面的切片。阶段 1 做完命令行能用，阶段 2 做完桌面端能切过来，阶段 3 做完本地协作群能用，阶段 4 是主动性和安全，阶段 5 是云端。
  • 每个切片开始前，执行模型先列出要动的公开接口和要测的行为清单，确认后再动手。
  • 桌面端切片编号 D1 到 D10，穿插在各阶段里，每片开头写明依赖的引擎切片。它们的规则一样：先写会失败的测试（渲染进程用 vitest 和引擎测试产出的黄金事件日志当夹具，主进程用 vitest，整条链路用 Playwright 对真实引擎），再写最少的实现。引擎切片和桌面端切片可以由两个人或两个执行模型并行做，桌面端切片做到它依赖的引擎切片完成为止。

S0 地基与 CI

S1 和假模型说上话

做完以后：merak debug chat --script testdata/hello.json "你好" 打印出假模型按剧本给的回答。

  1. 总线：发布一条事件，订阅者收到它，序号从 1 开始连续。
  2. 假模型：第一次请求得到剧本的第一条回复，多出的请求让测试失败。
  3. 会话：应用一条 message.sent 和一条 message.completed 后，消息列表是 user 和 assistant 两条。
  4. 循环：给一条输入，假模型回一句话，发布的事件依次是 turn.started、message.sent、message.completed、turn.finished。
  5. 命令行：命令打印回答并返回 0；没给剧本时返回 2。

只实现：事件包（事件结构、总线的发布和订阅，先不接存储）、模型包（接口、请求、消息、Part、Chunk、流、Collector，加假模型）、会话状态和 Fold（只处理消息事件）、循环（没有工具、没有插话）、debug 命令、platform/log 的最小配置。不做：存储、工具、权限、窗口、提示词组装（系统提示词先是一个常量）、订阅过滤。

S2 模型能读文件

做完以后：让模型总结 README，它先调用 read_file，再给出总结。

  1. 工具：read_file 返回文件内容；文件不存在时结果标为出错。
  2. 循环：模型回了一个工具调用，工具被执行，结果作为下一条消息送回，第二次请求的 Expect 能看到文件内容。
  3. 事件：tool.called 和 tool.completed 成对，后者的 Cause 指向前者。
  4. 重放等于实时：把全部事件从头 Fold 一遍得到的会话状态，和实时得到的完全相同。

只实现：工具包（接口、说明、调用、结果、环境里只有工作目录）、read_file、循环里的工具步骤（串行）、Fold 处理工具事件。不做：工具池（先用一个切片装工具）、并行执行、副作用枚举（先用一个“是否只读”的布尔值）、截断。

S3 改文件之前先问人

  1. 策略：每次询问模式下，读允许，写要问。
  2. 权限门：工具被挡住直到收到回复；允许后运行；拒绝后结果标为出错，模型知道被拒绝了。
  3. 事件：permission.requested 和 permission.replied 成对，Cause 对得上。
  4. write_file 写入；edit_file 要求被替换的文字唯一，匹配到两处就报错。
  5. 命令行从 stdin 读答案。

只实现：权限包（三种判断、每次询问模式、问人的接口、权限门）、两个写工具、stdin 答题。不做：记住选择、另外两档模式、路由、沙箱。

S4 接上真模型，边生成边打印

做完以后：设好环境变量就能和真实模型对话，文字一边生成一边打印。

  1. OpenAI 兼容客户端：对一个 httptest 服务器回放录好的 SSE 样例，解析出文字、工具调用和用量。
  2. 工具定义被正确转成它的格式。
  3. message.delta 按到达顺序发出，拼起来等于 message.completed 的全文。

只实现：三个搜索工具、时效检查、Spill 和 blob 文档（内存实现）、lookup、后台 bash、工具池、两个元工具。不做：web 工具、噪音过滤、MCP。

  4. 任务卡的形态默认值：项目是仓库时 worktree，否则 folder。

只实现：三种形态、发布、租约、默认值。不做：产物预览、复用。

S23 任务看板和收件箱的数据，工作周期，任务级 Leader

S25 沙箱覆盖所有成员进程

做完以后：每次询问和仅询问危险行为两档下，任何成员进程（内置 bash、Claude Code、Codex、opencode、pi）都读不了凭据目录、写不了工作区以外的目录和保护路径、连不了没允许的网络；本机做不到其中某项时 Status 如实报告，策略按 10.3 节降级；全面接管模式从这一片起可选，选了就关沙箱；CI 多了三个系统的沙箱一致性 job。

  1. 每个系统一份一致性测试：在沙箱里跑一个试图写工作区外文件的命令，失败；写工作区内，成功；读 ~/.ssh，失败；写 .git/hooks，macOS 和 Windows 失败，Linux 断言 Status 报未强制且退出后文件被还原、错误里列出该路径；不存在的保护路径断言报缺失且没有被预建；访问未允许的网络，有网络强制时失败，没有时断言 Status.Network 为 none；通配规则 *.example.com 放行子域、不放行裸 IP 和顶域本身，拒绝列表压过允许列表。Windows 另加三条：写盘根下的一个目录，失败；同时启动两个认领，一个成员写另一个的工作区，失败；账户用完时第三个认领排队；Status.Limits 报 loopback-open，pi 和纯命令成员不因此多问；空闲会话占着的账户被新认领收回，会话下一轮重新租到。
  2. 三个系统共用的日常工具用例：git --version、git status、node 打印一行、node 往 TEMP 写一个文件、读用户资料目录下 ReadDeny 之外的一个普通文件、在工作区里用用户的全局身份 git commit，都成功；退出码、UTF-8 输出和参数原样回传。Windows 另加：node 用默认管道再起一个子进程成功；管道和 ConPTY 两种标准流接法都覆盖；成员进程看不到用户的交互窗口站（读不到剪贴板）；凭据失效后 Status 翻为不可用、恢复后翻回；助手自身启动失败和成员退出码 125 区分开，前者让 Status 翻为不可用，后者不影响。
  3. 所有运行器都经 sandbox.Command 启动；环境变量按白名单透传，TEMP 和 TMP 改指私有目录，Windows 上再加 git 的 safe.directory；适配器把产品状态目录加进 WriteAllow、其他产品的加进 ReadDeny；全面接管下返回不加限制的进程。
  4. Status 报告不可用时，能转发审批的成员每个非只读调用都问人；不能转发的成员启动前问一次，拒绝则启动失败并有自己的错误码。
  5. 识别到的沙箱拒绝记进 tool.completed 的错误；代理的拒绝带主机名和成员名；回滚动过的文件列在同一处。
  6. 一次运行的网络白名单按 10.3 节合成：档案 Network、群 AllowedHosts、单聊的用户配置。

只实现：三个系统的沙箱（macOS 的以 CI 为准，3.8 节）、保护路径回滚、Status、Windows 的助手子命令、接入所有运行器、全面接管模式、档案的 Network 字段、CI 的 sandbox job（Windows 一次性初始化和重置脚本，并删掉工作流里指向 v0.3 沙箱脚本的 external-network 步骤）。不做：Linux 的挂载命名空间和 seccomp、没有沙箱机制的系统上的替代方案、工作区配置的确认机制（10.5 节，S27 随 MCP 服务器一起做）。

S26 仅询问危险行为模式与审批路由

做完以后：该模式下工作区内的写入不再问人，工作区外的和保护路径问 admin，合并问 owner；群里常规审批先到任务线程的 Leader，Leader 拿不准问人；超时任务受阻。

  1. 策略：该模式的允许和要问的类别各一个用例；保护路径；用户规则里的命令前缀。
  2. 路由：常规类别先到任务线程的 Leader，有 approver 在线也一样；Leader 升级后和其他请求一样按角色找人，参与者优先；审核、计划确认和 Leader 自己发起的请求直接给人；admin 和 owner 级别的 Leader 批不了。
  3. 超时从第一次请求算起（Leader 升级不重新计时），到了转受阻并通知 owner；“记住这次选择”写进配置。
  4. 超预算（10.2 节“超预算”）：认领撞到任务卡或档案的上限后任务受阻；Leader 经 update_task 加预算产生 budget 请求到 owner，Leader 自己批不了；批准后任务卡多一条 grant，派回原成员后原会话在新上限内继续；拒绝后任务保持受阻；owner 经 task.update 加预算直接生效；单聊里 session.send 带 extendBudget 再给一份档案预算，不带的被拒。

只实现：该模式的策略、路由算法、approve 工具、超时、记住选择、超预算的申请和 grant、单聊的 extendBudget。不做：规则编辑界面、按成员或按群的总预算。

S27 MCP：客户端与服务端

做完以后：用户配置和确认过的工作区配置里的 MCP 服务器，它们的工具成为延迟工具；外部 Worker 经 merak mcp --claim C --as worker 拿到群工具并能交结构化报告；merak mcp --thread T --as leader 能把编排工具暴露给外部程序。

  1. 配置：解析两个文件名、注释和尾逗号、两个文件同时存在、未知字段、字段校验；用户配置与工作区同名时用户的生效；config.get 不给 env 的值。
  2. 确认：工作区的服务器第一次出现时不启动并发出 workspace 请求；确认后下一次会话启动它；拒绝后不再问；改了这一项会再问，改注释或别的服务器不会；同一项目的另一个工作树不再问。
  3. MCP 客户端在沙箱里连一个测试用的 MCP 服务器，它的工具成为延迟工具 mcp__服务器名__工具名，经 load_tools 和 call_tool 可用；启动失败的服务器被跳过，会话照常继续。
  4. ACP：merak acp 的 session/new 带一台 stdio 服务器，它的工具这条会话就可用；带 http 或 sse 的被拒；用户配置里的同名服务器优先；工作区的确认请求以 session/request_permission 送到客户端。
  5. MCP 服务端（worker）：一个测试客户端能调 submit_report，报告出现在任务上；Claude Code 假二进制经 --mcp-config 连上它。
  6. MCP 服务端（leader）：一个测试客户端能调 create_task，任务出现在线程的任务子树里；越权（在别的任务下建任务）被拒。

只实现：10.5 节的 mcpServers（用户配置、工作区文件、ACP 客户端传入）、workspaceTrust 确认记录、stdio 的 MCP 客户端、MCP 服务端两种角色、各适配器的 MCP 挂载配置、Caps.MCP。不做：远程 MCP 服务器、config.set 和设置页编辑 MCP 服务器、工作区配置的其他字段、技能、插件。

S28 外部产品当 Leader

做完以后：可以指定 Claude Code 当一个任务的 Leader，它通过 MCP 建子任务、派工、批审批、在讨论串里回复人。

  1. 调度器把摘要经 Send 送给外部 Leader（假二进制），它调 MCP 工具，群状态按预期变化。
  2. 路由给该线程的审批以消息送达，它调 approve 回答。
  3. 队长提示词作为第一条消息送达，内置 Leader 和外部 Leader 用同一份模板。

只实现：Leader 侧的运行器抽象（内置和外部走同一个调度器）、队长模板。不做：外部 Leader 的上下文管理。

S29 worktree 优化，限流与哨兵

做完以后：认领开始时自动跑安装命令；用过的 worktree 复用，node_modules 不用重装；每条线程和每个群都有每分钟次数上限，两个数在群设置里可改；哨兵发现卡住、死进程、原地打转、预算烧得太快时提醒相关的人和线程。

  1. setup 命令在工作区建好后运行一次，失败时任务受阻并附日志。
  2. 复用：释放的 worktree 被下一个认领重置后使用，被 git 忽略的目录保留。
  3. 限流（6.2 节 TurnLimits）：线程超过每分钟次数、群合计超过每分钟次数时事件继续攒着，快速通道照常，不发事件；名额空出来时没有新事件也会自己醒来，攒着的事件一个不丢地进下一批；群设置没写 turnsPerMinute 时用 6 和 30；改了以后下一次唤醒就按新值；0、负数和非整数被 group.update 拒绝。
  4. 哨兵：6.2 节表里的每条规则一个测试；发现时发 sentinel.flagged 并路由到线程和收件箱；每分钟检查一次，不调模型。

只实现：安装命令、复用池、两项每分钟限制和群设置的 turnsPerMinute、哨兵的八条规则。不做：每小时的 token 和费用上限、按成员的预算、用模型判断“是否在原地打转”。

D9 权限模式、沙箱状态、上下文与花费

做完以后：设置里能选三档权限模式并看到风险提示；对话和群里能看到沙箱状态（可用、部分强制、不可用、已关闭）；每条会话有“上下文花在哪了”，每个群有按任务和成员汇总的 token 和费用；群设置里能改线程和群的每分钟次数；哨兵的提醒进收件箱。

依赖：D7、S25 沙箱、S26 仅询问危险行为模式、S29 限流与哨兵。

  1. 权限模式选择器：复用权限级别组件和接管确认对话框；选全面接管时弹风险提示；经 config.set 生效。
  2. 沙箱状态：复用沙箱控制组件（含 Windows 的一次性初始化入口）显示可用、部分强制（列出未强制的项）、不可用、已关闭四种状态。
  3. 上下文与花费视图：session.budget 画成分段条；turn.finished 的用量按任务和成员汇总成表，费用按币种分列，不换算，未知费用显示“未知”。
  4. 每分钟次数：群设置里两个数字输入框（线程、群），显示当前值或默认值 6 和 30，经 group.update 保存；没有改群设置权限的人只读；引擎拒绝的值显示错误码。
  5. sentinel.flagged 进收件箱并发系统通知。

只实现：选择器、沙箱状态、花费视图、每分钟次数的两个输入框、哨兵通知。不做：权限规则编辑界面、群设置的其他项、按成员设预算。

S31 远程 MerakCode 成员

做完以后：局域网里另一台电脑上 merak serve 名下的任何成员都能作为 Worker 拉进本地群；它改的代码经仓库远端回到本机合并。

  1. 两个真实的 merak serve 在随机端口上：A 列出 B 的成员和它们声明的检出；A 把一个 none 任务派给 B 的成员，事件和报告在 A 的群流里出现。
  2. 往返：一个裸仓库当远端，A 和 B 各有检出，A 的群项目是 A 的检出；一个 worktree 任务派给 B 的成员，B 在自己的检出里建 worktree 干活，request_merge 时推分支；A fetch 后合并队列变基、跑检查命令、快进，merge.done 在 A 的流里出现，远端上的分支被删掉。
  3. 拒绝：把远程成员设为默认 Leader 或任务 Leader；给远程成员派 folder 任务；群项目没有远端时派 worktree 任务。三种都返回错误码。
  4. B 断线：它名下进行中的认领在 A 这边标为中断。

只实现：remote 适配器（经 Go 协议客户端）、手动填地址和令牌、注册时声明检出、worktree 和 none 两种形态、经远端的往返。不做：自动发现、远程 Leader、远程成员的 folder 和 inplace 形态、跨设备传产物文件。

16. 测试怎么做

16.1 节奏：一次一个

每个切片先做计划：列出要动的公开接口和要测的行为清单。然后一个行为一轮：红，写一个描述这个行为的测试，运行，看着它失败，贴出失败的输出；绿，写刚好够让它通过的代码，允许写死；整理，在测试保护下去重、改名、拆函数，不加新行为。不允许先写完一个切片的所有测试再写实现。想到的其他用例先记在测试文件末尾的注释里。

16.2 测行为，不测实现

测试只通过公开接口说话：给循环一条输入，断言发出的事件序列；给任务池一次派工，断言状态；给存储一串事件，断言能查回来。不测私有函数，不 mock 内部协作者。判断标准：重命名一个内部函数、改一个内部结构体，测试不该坏；行为变了，测试必须坏。

16.3 三层测试

层 测什么 怎么写
契约测试 一个包对外承诺的行为：任务池的派工规则、窗口的重建、会话的 Fold、存储的七个方法 表格形式，放在包里。几个实现共享的测试（存储、运行器）写成一个函数，每个实现调用它
切片测试 用户能看到的行为：从命令行或协议进，用假模型剧本，断言事件序列和输出 放在 cli 或 server 包的测试里。剧本和黄金事件日志放 testdata/
冒烟测试 真实的模型、真实的产品二进制 没有密钥或二进制时跳过。不放在 CI 的必经路径上

16.4 让测试说真话

  • 假模型的 Expect：断言模型在第 n 次请求里看到了该看到的东西，比如工具结果、重建后的摘要、群状态。Hold 让流卡住，用来测抢占。
  • 黄金事件日志：时钟和 id 生成器可注入，同一个剧本跑出来的事件日志逐字节可比。更新黄金文件用 -update 标志，并在提交里看一眼 diff。
  • 重放等于实时：每个 Fold 都有一条测试，“把全部事件重放一遍得到的状态，等于实时一条条更新得到的状态”。重建、崩溃恢复、子智能体结果插入尤其要有。
  • 不用 mock：存储用内存实现；git 用临时目录里的真仓库；外部产品用 go build 编出来的假二进制；协议用随机端口上的真服务端；模型用假模型；云端用测试里起的假云端。
  • 竞争检测：go test -race 在 Linux 的 CI 上跑。调度器、线程、合并队列、缓冲存储、成员队列的测试专门覆盖并发。

17. 防止过度设计的清单

每个切片结束时对一遍。违反了哪条，就在这个切片里改掉。

  1. 字段按切片加。第 4 到 10 节的结构体是最终形状，一个切片只加它的测试用到的字段。
  2. 接口要有两个实现才抽象。只有一个实现就用具体类型。例外是从第一天起就有两个实现的：模型接口（假模型和 OpenAI 兼容）、存储契约（内存和远程）、运行器（内置和 Claude Code，从 S17 起）。
  3. 常量先写死。重建阈值、保留轮数、工具输出上限、静默窗口、超时、哨兵阈值都先是常量，第二个人要改时再变成配置。
  4. 不写规则语言。触发规则的条件只支持路径 glob；权限规则只支持路径前缀和命令前缀。
  5. 不预留。不为“以后”留字段、接口、TODO、空包。能力清单只有三项。
  6. 包从少开始。允许先把 profile 放在 group 里、把材料包放在 leader 里，有第二个使用者再拆。engine/ 下不超过两层。
  7. 不提前优化。缓存、批量、并行都等测量以后再加。例外是只读工具并行执行，它决定事件顺序，必须一开始定下来并写进测试。
  8. 做删除检查。切片结束时：只有一个实现也没有测试要求的接口，内联掉；没有调用者的导出删掉（go vet 加 staticcheck）；为测试方便加的导出改回小写。
  9. 文档跟着代码走。实际形状和文档不一样时改文档，不改代码去迁就文档。
  10. 一个切片一个提交能讲清楚。改动超过 1500 行、动到 4 个以上的包，或者动手前要先做两次以上的设计讨论，就拆开；拆不开说明设计有问题，回到讨论。
