这份文档是什么

这是一份施工单。它要做的是：把仓库里上午建的 TypeScript 引擎骨架换成 Go 程序的骨架，再把检查工具和说明文档改成 Go 的规则。

它不设计任何引擎功能。引擎的模块怎么分、协议怎么定，由你之后自己设计。

做完以后你会得到什么

  • 一个 Go 程序 merak，放在 apps/merak。它能编译、能测试，现在只会输出版本号。
    • apps/merak 不是某一层，而是整个程序。仓库约定 apps/ 放能运行的程序，packages/ 放给别人引用的库。
    • 命令行、接口、智能体引擎都在这个程序里，用 internal/ 下的不同包分开。分层见附录 A.4。
    • 地基只建了入口和命令行的最小部分。智能体引擎没有建，要等你一个模块一个模块地设计。
  • 一条命令就能编出 6 个平台的程序：Windows、macOS、Linux，各有 x64 和 arm64 两种。
  • pnpm check 会自动检查 Go 代码，一共查三样：格式对不对；在三个系统上能不能编译；注释里有没有中文。
  • AGENTS.md 和 CONTRIBUTING.md 写好了 Go 的规则。以后 AI 写代码时会照着这些规则做。

// Package merak holds what the whole merak program shares: the product version.
package merak

import (
	_ "embed"
	"encoding/json"
)

// manifest is the package.json next to this file. The version lives there so that pnpm release:version sets it for
// every package at once.
//
//go:embed package.json
var manifest []byte

// Version returns the product version from package.json.
func Version() string {
	var pkg struct {
		Version string `json:"version"`
	}
	if err := json.Unmarshal(manifest, &pkg); err != nil {
		panic(err)
	}
	return pkg.Version
}

apps/merak/script/check.ts

/**
 * The Go module's typecheck: gofmt, then go vet once per target system without cgo, so code that only builds on one
 * system fails on every machine.
 *
 * Usage (in apps/merak): pnpm typecheck
 */
import { spawnSync } from "node:child_process"

const SYSTEMS = ["linux", "darwin", "windows"]

function run(command: string, args: string[], env: Record<string, string> = {}) {
  const result = spawnSync(command, args, { encoding: "utf8", env: { ...process.env, ...env } })
  if (result.error) throw result.error
  if (result.status !== 0) {
    process.stderr.write(result.stdout + result.stderr)
    process.exit(result.status ?? 1)
  }
  return result.stdout
}

const unformatted = run("gofmt", ["-l", "."]).trim()
if (unformatted) {
  console.error(`Not formatted; run gofmt -w on:\n${unformatted}`)
  process.exit(1)
}
for (const system of SYSTEMS) run("go", ["vet", "./..."], { GOOS: system, GOARCH: "amd64", CGO_ENABLED: "0" })

apps/merak/script/build.ts

/**
 * Builds merak without cgo for every release platform, into dist/<platform>-<arch>/. Platform names match the
 * release packages, merakcode-<platform>-<arch>.
 *
 * Usage (in apps/merak): pnpm build
 */
import { spawnSync } from "node:child_process"
import path from "node:path"

const TARGETS = [
  { platform: "linux", arch: "x64", goos: "linux", goarch: "amd64" },
  { platform: "linux", arch: "arm64", goos: "linux", goarch: "arm64" },
  { platform: "darwin", arch: "x64", goos: "darwin", goarch: "amd64" },
  { platform: "darwin", arch: "arm64", goos: "darwin", goarch: "arm64" },
  { platform: "windows", arch: "x64", goos: "windows", goarch: "amd64" },
  { platform: "windows", arch: "arm64", goos: "windows", goarch: "arm64" },
]

for (const target of TARGETS) {
  const name = target.goos === "windows" ? "merak.exe" : "merak"
  const output = path.join("dist", `${target.platform}-${target.arch}`, name)
  const build = spawnSync("go", ["build", "-trimpath", "-ldflags=-s -w", "-o", output, "./cmd/merak"], {
    env: { ...process.env, GOOS: target.goos, GOARCH: target.goarch, CGO_ENABLED: "0" },
    stdio: "inherit",
  })
  if (build.error) throw build.error
  if (build.status !== 0) process.exit(build.status ?? 1)
  console.log(output)
}

平台名和现有发布包一致：linux、darwin、windows 各有 x64 和 arm64。根目录 .gitignore 已经忽略 dist，不用改。

步骤 6：knip 配置和依赖安装

做什么：让 knip 认识新目录，然后重新安装依赖。为什么：knip 会检查有没有没用到的文件。不告诉它新目录里的脚本是入口，它会把这两个脚本误报成没用到的文件。

  1. 打开根目录 knip.json。
  2. 在 "workspaces" 里加一项，放在 "apps/desktop/main" 那一项后面： 
        "apps/merak": {
      "entry": ["script/*.ts"]
    },
  3. 在仓库根目录运行 pnpm install。
  4. 运行 pnpm check:unused。
  5. 如果它报 apps/cli 引用了没登记的 @merakcode/engine，就在 knip.json 的 "apps/cli" 那一项里加一个字段： 
          "ignoreDependencies": ["@merakcode/engine"]
    然后再运行一次 pnpm check:unused。
  6. 如果它报 apps/merak 用了没登记的命令 go（Unlisted binaries），就在 knip.json 顶层的 "ignoreBinaries" 数组里加上 "go"，再运行一次。

/**
 * Comments and t.Run titles in Go. Interpreted strings, raw strings and runes are skipped whole, so `//` inside one
 * starts no comment.
 */
function goIssues(text: string): Issue[] {
  const starts = [0, ...[...text.matchAll(/\n/g)].map((match) => match.index! + 1)]
  const line = (offset: number) => starts.findLastIndex((start) => start <= offset) + 1
  const end = (from: number, close: string) => {
    const at = text.indexOf(close, from)
    return at < 0 ? text.length : at + close.length
  }
  const comments: { start: number; text: string }[] = []
  const literals: { start: number; text: string }[] = []
  let i = 0
  while (i < text.length) {
    const pair = text.slice(i, i + 2)
    const quote = text[i]!
    if (pair === "//" || pair === "/*") {
      const stop = pair === "//" ? end(i, "\n") : end(i + 2, "*/")
      comments.push({ start: i, text: text.slice(i, stop) })
      i = stop
    } else if (quote === "`") {
      const stop = end(i + 1, "`")
      literals.push({ start: i, text: text.slice(i, stop) })
      i = stop
    } else if (quote === '"' || quote === "'") {
      let stop = i + 1
      while (stop < text.length && text[stop] !== quote && text[stop] !== "\n") stop += text[stop] === "\\" ? 2 : 1
      literals.push({ start: i, text: text.slice(i, stop + 1) })
      i = stop + 1
    } else i++
  }
  const allowed = new Set(
    comments
      .filter((comment) => comment.text.includes("i18n-allow"))
      .map((comment) => line(comment.start + comment.text.trimEnd().length - 1) + 1),
  )
  const found = new Map<number, Issue>()
  for (const literal of literals) {
    const at = line(literal.start)
    if (CJK.test(literal.text) && /\bt\.Run\(\s*$/.test(text.slice(starts[at - 1]!, literal.start)))
      found.set(at, { line: at, kind: "test", text: literal.text })
  }
  for (const comment of comments) {
    const at = line(comment.start)
    if (CJK.test(comment.text) && !found.has(at))
      found.set(at, { line: at, kind: "comment", text: comment.text.replace(/^\/[/*]|\*\/$/g, "").trim() })
  }
  return [...found.values()].filter((issue) => !allowed.has(issue.line)).sort((a, b) => a.line - b.line)
}

# MerakCode development notes

Monorepo for MerakCode, an AI coding tool: an Electron desktop app (the main product), a `merak` command line without a UI, and a TypeScript SDK. The `merak` program (command line and engine) is being rewritten in Go; the desktop app, the SDK and the repository scripts are TypeScript (ESM) on Node.js 26.12+ with pnpm 12. This file lists what is easiest to get wrong; [CONTRIBUTING.md](CONTRIBUTING.md#contributing) is the full guide.

## v1.0.0 rebuild

The `dev-v1.0.0` branch rewrites the `merak` program from scratch in Go, in `apps/merak`. The user designs each module: implement what the user has decided, and ask when a design question is still open.

- Architecture: the Go program `merak` is the engine and the backend, and owns all logic and data. Electron is only the user interface: its main process handles windows, the tray, notifications, updates and starting the engine, and its renderer shows things and takes input. Both reach the engine through `@merakcode/sdk` and never read the engine's files.
- The local product works fully without any cloud service. A cloud service will come later as a separate program in a separate private repository; it only adds features. Don't add cloud code to this repository.
- Don't read, search or copy the v0.3 engine (the `v0.3.0` tag, other branches, or other clones of this repository) unless the user asks. Don't copy code from other coding agents either; some Go ones are not under an open source license. Work from the user's design and from tests.
- `apps/cli` is the v0.3 command line in TypeScript. It stays until its commands are ported to `apps/merak`; read it only to port a command the user asks for. `pnpm typecheck` leaves it out, and its tests fail.
- The desktop app and the SDK still speak the v0.3 engine's protocol; they move to the new one once it exists. Until then `check:sdk` and `check:adapter-library` are left out of `pnpm check` (`generate:sdk` and `generate:adapter-library` fail too), tests that start an engine (in `packages/sdk/js` and the desktop end-to-end tests) are expected to fail, and `.github/workflows/ci.yml`, which runs only on pull requests and pushes to `main`, still describes v0.3.

## Layout

- `apps/merak` — the Go module of the `merak` program. `cmd/merak` is its entry, every other package is under `internal/`, and the module root package reads the product version from the `package.json` next to it. That `package.json` only wraps the Go commands for pnpm and turbo. See [Go code](#go-code).
- `apps/cli` — the v0.3 command line in TypeScript, waiting to be ported (see above).
- `packages/sdk/js` — the TypeScript SDK (`@merakcode/sdk`): engine launcher, high-level API, event store, plugin and adapter types, errors, transcript export. It is hand-written and editable, except `src/client/gen/` and `packages/sdk/openapi.json`, which are generated from the v0.3 server's OpenAPI spec; never edit those by hand.
- `packages/util`, `packages/log` — shared TypeScript helpers, the error code catalog, logging.
- `apps/desktop/main` — Electron main process; starts the bundled engine.
- `apps/desktop/renderer` — desktop UI (SolidJS + Vite, plain CSS with design tokens; no `!important`).

## Go code

- Use the Go version named in `apps/merak/go.mod`. Run Go commands inside `apps/merak`, or through its scripts: `pnpm --dir apps/merak test` runs `go test ./...`, `typecheck` runs gofmt and then `go vet ./...` for Linux, macOS and Windows, and `build` builds every release platform into `dist/`.
- No cgo: everything builds with `CGO_ENABLED=0`, so one machine builds every platform. `go test -race` needs cgo, so it is not part of the local checks.
- Every package is under `internal/`, except `cmd/merak` and the module root. Go itself rejects import cycles between packages.
- Standard library first. Add a module to `go.mod` only for a reason the user agrees with.
- Format with gofmt; `pnpm --dir apps/merak typecheck` fails on unformatted files.
- Tests are table-driven when cases share a shape, use `t.TempDir()` for temporary directories, and test real behavior without mocks.
- Comments and `t.Run` titles are in English; `check:comments` checks Go files too.
- Text for users needs Chinese and English, and the Go side has no mechanism for that yet. Until the user designs one, `apps/merak` prints no text meant for users.

## Commands

- `pnpm check` at the root runs `format:check`, `check:brand`, `check:comments`, `check:versions`, `check:errors`, `typecheck`, `check:deps`, `check:css`, `check:api`, `check:sdk-reference`, `check:sdk-docs`, `check:docs` and `check:unused`, in that order ([what each one checks](CONTRIBUTING.md#commands)); `typecheck` includes the Go checks of `apps/merak`. Run it before finishing a change. It runs no tests; run `pnpm test:script` and the tests of the packages you changed as well.
- Tests run per package: `cd <package> && pnpm test [file]`. `pnpm test` at the root only fails; the root `script/` folder is tested with `pnpm test:script`.
- Tests need `rg` (ripgrep) on PATH; without it every test process downloads its own copy from GitHub.
- End-to-end tests use real processes and a local fake model: `apps/cli` → `pnpm test:e2e` (the engine driven through the SDK); `apps/desktop/main` → `pnpm test:e2e` (launches the Electron app; build main and renderer first). Both still target v0.3.
- Never edit generated files; regenerate them. After error codes: `pnpm generate:errors`. After changing the SDK's public API on purpose: `pnpm check:api --write`.

## Conventions

- TypeScript: Prettier with no semicolons and 120 columns. The compiler rejects unused variables and imports (except in `packages/sdk/js`), and knip unused files, exports and dependencies. Nothing checks for commented-out code; don't leave any, in Go either.
- Validate TypeScript inputs with Zod.
- Code comments, log messages and test titles are in English; `check:comments` fails on Chinese in them (a `// i18n-allow` comment lets the next line through). User-facing text needs Chinese and English: `apps/cli/src/cli/locales/{zh-CN,en-US}.json` (keys must match and be used) and `apps/desktop/renderer/src/i18n/{zh,en}.ts`. Model-facing prompts and tool descriptions are English only.
- Dependency boundaries (`check:deps`, TypeScript): the desktop app and the packages never import `apps/cli`; client code reaches the engine only through the SDK's generated methods, never its own `fetch`, `WebSocket` or `node:http`; module names are string literals. See [Boundary rules](CONTRIBUTING.md#boundary-rules).
- Logging in TypeScript: `Log.create({ service })` from `@merakcode/log/logger` in the CLI, `Log.create(service)` from `src/log.ts` in the desktop main process, `log()` from `src/lib/bridge.ts` in the renderer. Don't use `console.*` for diagnostics, and never log keys, passwords or conversation content.
- An error a user can see needs an `MRK-xxxx` code in `packages/util/src/error-code.ts`: the thousands digit matches its `domain`, and `title` and `hint` have both `zh` and `en`. Then run `pnpm generate:errors`. See [Error codes and logs](CONTRIBUTING.md#error-codes-and-logs).
- TypeScript tests use Vitest against real behavior; avoid mocks. Use a `tmpdir()` fixture for temporary directories and a local fake model for replies.
- Prefer early returns over `else`, `const` over `let`, and small focused functions.
- A change users will notice gets a line under `Unreleased` in `CHANGELOG.md`, in both the English and the Chinese section. See [Pull requests](CONTRIBUTING.md#pull-requests).
- Commit messages follow [Commit messages](CONTRIBUTING.md#commit-messages). Never add `Co-authored-by` or other attribution lines to commits or pull request descriptions.

A.1 先记住 6 条规则

下面都是 Go 语言本身的规则，已确认。

  1. 一个目录就是一个包。同一目录里的 .go 文件属于同一个包。
  2. 包名和目录名相同。包名用小写、简短、单数的词，不用下划线。比如用 session，不用 sessions 或 session_store。
  3. 首字母大写的名字，其他包可以用。首字母小写的名字，只能在本包里用。
  4. 包之间不能循环引用，编译器会直接报错。
  5. internal/ 下的包，只有 internal 的父目录及其子目录里的代码能引用。cmd/<程序名>/ 放程序入口，也就是 main 包。
  6. 文件名的后缀有特殊含义：
    • _linux.go、_darwin.go、_windows.go 只在对应系统上编译。
    • _test.go 是测试文件。
    • go 命令会忽略名叫 testdata 的目录，测试用的样例文件放在这里。

Go 官方的布局说明在 go.dev/doc/modules/layout。网上流行的 golang-standards/project-layout 不是官方标准。据我所知，它的说明里自己写明了这一点。

A.2 你问的“agent 目录下放很多子目录”

结论：这是常见做法，可以用。前提是每个子目录都是一个职责清楚的包。下面是 5 个注意点。

  1. 父目录 agent 和子目录 agent/loop 是两个独立的包。目录上的父子关系不带来任何特殊权限，子包也看不到父包里首字母小写的名字。
  2. 不要把公共类型放在父包里，又让父包引用子包，这样会形成循环引用。几个包都要用的类型，单独放进一个小包。
  3. internal/ 下面最多嵌套 3 层。层级太深时 import 路径会变长，通常也说明包拆得太碎了。
  4. 按业务领域分包，比如 session、tool、model。不要按技术层分包，比如 models、services、controllers。Go 社区普遍不推荐 utils、common 这类包名。
  5. 开始时少分包。一个包里放多个文件很正常，等一个包变得难理解了再拆。

A.3 依赖方向怎么定

  • 先定好谁可以引用谁。比如 agent/loop 可以引用 tool 和 model，tool 不能反过来引用 agent/loop。
  • 下层的包需要调用上层功能时，由下层的包定义一个接口，上层把实现传进来。Go 的接口不需要显式声明“我实现了它”，只要方法对得上就算实现。
  • 由一个地方创建所有模块，并把每个模块需要的东西传进去。在 A.4 的分层里，这个地方是 internal/engine 的 New 函数。只有它引用所有引擎模块；引擎模块不引用它。

B.0 一条消息怎么从桌面端走到 Go 引擎

先定义三个词：

  • 进程：一个正在运行的程序。桌面端是一个进程，Go 引擎是另一个进程。
  • 协议：两个进程之间约定好的消息格式。比如“发送一条消息”的请求长什么样，“模型输出了一段文字”的事件长什么样。
  • SDK：给调用方用的库。它把协议包装成普通的函数，调用方不用自己拼消息。

用户在桌面端发一条消息时，按下面的顺序发生：

  1. 桌面端启动时，运行 merak.exe serve。Go 引擎作为一个单独的进程在后台运行，没有窗口。
  2. 用户在界面里输入“帮我修这个 bug”。
  3. 界面代码调用 SDK 的一个函数，比如“发送消息”。界面代码是 TypeScript 写的，所以 SDK 也是 TypeScript 写的。
  4. SDK 把这次调用变成一条协议消息，通过本机连接发给 Go 引擎。
  5. Go 引擎的接口层收到消息，交给引擎层。引擎层开始跑 agent 循环：请求模型、执行工具、再请求模型。
  6. 引擎每做一步，就发一条事件消息回去。SDK 收到后交给界面，界面把它显示出来。
进程 1：桌面端（Electron，TypeScript 写的）
  界面代码
    调用 @merakcode/sdk 的函数（TypeScript 库）
      │
      │  通过本机连接收发协议消息
      │
进程 2：merak.exe serve（Go 写的，在后台运行）
  接口层：收消息，交给引擎层；把事件发回去
  引擎层：agent 循环、模型、工具、会话、权限等

为什么 SDK 用 TypeScript 写，引擎用 Go 写

SDK 要用调用方的语言写。调用方是 Electron，它的代码是 TypeScript，所以 SDK 用 TypeScript 写。SDK 里没有 Go 代码，它只负责收发消息。

你用过的 OpenAI Python SDK 就是这种关系：

真正干活的程序 SDK 两者之间
OpenAI OpenAI 的服务器。它用什么语言写，调用方不用关心 pip install openai，Python 写的 HTTP 请求
MerakCode merak.exe serve，Go 写的 @merakcode/sdk，TypeScript 写的，给 Electron 用 本机协议

以后如果有 Python 程序想调用 MerakCode，就再写一个 Python 的 SDK，Go 引擎不用改。

为什么不把 Go 代码直接编成库，给 Electron 调用

  • 技术上能做，但要用 cgo 和 Node 的原生扩展。这和“不用 cgo”的规定冲突，每个平台还要单独处理。
  • 引擎和界面在同一个进程里，引擎崩溃时界面也会跟着崩溃。
  • 命令行和桌面端就没法共用同一个正在运行的引擎。
  • 已确认：旧版本就是分成两个进程。旧仓库里接入 Codex 的适配器，也是先启动 codex app-server 进程，再通过协议和它通信。

命令行在哪里

  • CLI 就是命令行，也就是你在终端里输入的命令。在终端输入 merak run "帮我修这个 bug"，和输入 python main.py、git commit 是一回事。
  • 命令行和引擎是同一个程序 merak.exe。merak serve 启动引擎；merak run 让引擎做一个任务，并把过程打印在终端里。
  • 命令行是 Go 写的，和引擎在同一个程序里，所以不需要 SDK，可以直接使用引擎的代码。
  • 有一个细节以后设计接口层时再定：merak run 是在自己的进程里直接跑引擎，还是连到一个已经在运行的 merak serve。附录 A.6 和 B.2 讲了这个选择。

和旧版本对照

部分 旧版本（TypeScript） 新版本（Go）

merak 程序 apps/cli：serve 命令加载引擎；其他命令用 TypeScript SDK 连到引擎 apps/merak：serve 命令启动引擎；其他命令直接使用同一个程序里的引擎代码，或者连到正在运行的 serve（以后再定）

为什么 Go 不需要单独的 packages/engine：

  • 在 TypeScript 仓库里，代码要分开管理，就得做成单独的 npm 包，放进 packages/，再用 check:deps 检查谁能引用谁。
  • 在 Go 里，一个目录就是一个包。internal/ 的访问限制和禁止循环引用都由编译器检查。所以同一个 Go 模块里就能把命令行、接口、引擎分清楚，不需要拆成多个顶层目录。
  • 已确认：旧版本发布时，引擎和命令行本来就打包成同一个程序，只是源码分在两个目录。新版本只是把源码也放进了同一个模块。
  • TypeScript 代码不能直接引用 Go 代码，所以引擎也没有别的使用方。以后私有的云端仓库需要复用某些包时，再把它们移出 internal/（见附录 C.1.1）。

B.2 一个数据目录只跑一个引擎（建议）

  • 已确认：现在每个客户端都会用 startEngine 自己启动一个引擎进程。桌面端和 CLI 同时使用时，两个引擎读写同一份数据，靠共享锁协调。
  • 建议：每个数据目录只运行一个引擎进程。客户端先尝试连接，连不上再启动引擎。
  • 依据一（推断）：数据只有一个写入方，就不需要跨进程的锁。
  • 依据二：定时任务和协作群需要一个长期运行的进程。已确认旧引擎有定时任务模块。
  • 要设计的点：谁负责停止引擎，比如没有客户端连接一段时间后自动退出；引擎崩溃后谁负责重启。

B.3 连接时先交换版本（建议）

  • 问题（推断）：用 npm 装的 CLI 和桌面端内置的引擎，版本可能不同。只跑一个引擎时，旧客户端可能连到新引擎上。
  • 建议：连接后的第一条消息交换协议版本号。版本不兼容就拒绝连接，并提示用户升级。
  • 数据目录的格式升级只由引擎来做。

B.4 本机连接方式和安全

  • 已确认：现在引擎监听 127.0.0.1 的随机端口，用一次性密码认证，密码通过环境变量传给引擎。
  • 只跑一个引擎时，有两种做法：
    • 本机 socket（Unix 上是 Unix socket，Windows 上是命名管道）：其他机器和浏览器都连不到。代价有两个：据我所知，Go 标准库不支持 Windows 命名管道，要加 go-winio 依赖；Electron 界面进程不能直接连 socket，要经过主进程转发。
    • 127.0.0.1 端口加令牌：Go 和 Electron 都只用标准接口。代价是本机任何程序都能尝试连接，所以必须校验令牌，WebSocket 还要校验 Origin。
  • 我的建议：用 127.0.0.1 端口加令牌。引擎把端口和令牌写进数据目录里一个只有当前用户能读的文件，客户端从这个文件读取。理由是两边都不用加依赖，界面进程也能直接连接。
  • 已确认旧引擎有局域网发现（mDNS）。建议协议不要绑定某一种传输方式，以后要加远程访问时，只需要多加一种传输。

B.5 终端数据走单独的二进制通道（建议）

  • 终端输出是字节流，数据量大。放进 JSON 要先做 base64 编码，体积会增加约三分之一。
  • 建议：协议消息只传控制信息，终端字节用单独的 WebSocket 二进制帧传输。
  • 已确认：旧协议也为终端单独开了一条 WebSocket。

B.6 存储不能依赖 cgo

  • 方案规定不用 cgo。据我所知，最常用的 SQLite 驱动 mattn/go-sqlite3 需要 cgo。
  • 要用 SQLite，就选纯 Go 实现的驱动，比如 modernc.org/sqlite（据我所知）。另一种做法是只追加的 JSONL 文件，这样不用加依赖。
  • 这一点在设计存储模块时决定。

B.7 界面安全

  • 界面进程会显示模型输出的 Markdown。XSS 指页面里被注入了不受信任的脚本，并且执行了。推断：如果渲染时出现 XSS，恶意脚本就能通过 SDK 让引擎执行命令。
  • 建议：Markdown 渲染后做清洗；设置严格的 CSP（浏览器的内容安全策略，用来限制页面能加载和执行哪些脚本）；保持 contextIsolation 打开，nodeIntegration 关闭。
  • 权限判断必须在 Go 引擎里做。界面只负责显示审批，并把用户的选择传回去。

B.8 “后端”是否包括云端服务（不确定）

  • 我不确定你说的“后端”是否包括云端服务，比如账号或同步。
  • 如果包括，建议把云端服务写成单独的程序，不要放进本机引擎。理由（推断）：两者的部署方式、安全要求和发布节奏都不一样。
  • 用户已说明：云端服务默认会有，可能部署在阿里云上，以后可能有云端智能体。先做单机版，云端逐步加。具体准备见附录 C。

B.9 对外开放的三种接入方式（建议）

用户已决定：命令行要对外开放，方便其他产品接入。其他程序可以用三种方式使用 MerakCode，三种方式背后是同一个引擎和同一套协议。

方式 适合谁 要设计的点
协议 任何语言的程序，需要长期连接、实时接收事件 消息格式只在一个地方定义：用 Go 类型写，自动生成 JSON Schema。连接时先交换版本（见 B.3）
SDK TypeScript 程序，比如桌面端和第三方程序；以后可以加 Python 等语言 类型从协议的 JSON Schema 生成
命令行 其他产品、脚本、CI，只想“给一个任务，拿回结果” 提供机器可读的输出，比如每行一个 JSON 事件；保留 ACP 接入；参数和输出格式公开以后要保持兼容

旧仓库里有现成的参照（已确认）：

  • 旧的适配器接入 Claude Code 时，用的是 claude -p 的 stream-json 输出；接入 Codex 时，用的是 codex app-server 的 JSON-RPC。
  • 旧命令行有 merak acp 命令，用来对外提供 ACP 服务。
  • 旧 SDK 的客户端代码，是从服务端的 OpenAPI 描述文件自动生成的。新版本把服务端换成 Go，思路不变。

附录 C：为云端服务做准备

用户已决定两件事。第一，本机版本必须能单独完整使用，先做单机版，云端服务逐步加。第二，云端代码按多数产品的做法处理，也就是放在单独的私有仓库。

结论：云端服务写成单独的 Go 程序，放在单独的私有仓库。本机引擎访问云端的代码只放在一个包里。现在的地基不用改目录，只在 AGENTS.md 里加一条说明（已写进步骤 8）。

  1. 客户端开源，云端不公开：Cline、Continue、Roo Code。这是最多的一种。
  2. 云端代码可以看，但许可证不是开源协议，商用要授权：Kilo Code、OpenHands。
  3. 云端也开源：Zed 的协作服务器、opencode。

就连公开云端代码的产品，也会把一部分留作私有。比如 Kilo Code 不公开防滥用代码，Zed 的登录网站在另一个仓库。

按多数做法，MerakCode 的云端代码放在单独的私有仓库。我推断这样做还有一个好处：私有代码以后随时可以改成公开；代码一旦公开，就再也收不回来了。

Continue 和 Roo Code 关闭云端以后，本机插件仍然能用（Continue 是搜索结果明确写的）。这也印证了你的决定：本机版本要能单独完整使用。

C.1.1 私有仓库怎么复用本机代码

  • Go 的 internal/ 包不能被别的模块引用。云端要复用本机代码时，比如 agent 循环或模型客户端，这些包要移出 internal/，变成公开的包。公开的包要尽量保持接口稳定。
  • 做法：现在所有包都放在 internal/。云端真正需要某个包时，再把它移出来。Go 的 import 路径就是目录路径，移动一个包只需要改 import 路径。
  • 私有仓库引用这个公开模块时，可以直接用某个提交对应的伪版本，不需要专门打标签（据我所知）。
  • 云端和本机之间的接口类型（比如登录、同步的消息格式），可以放进公开模块的一个公开包里，两边共用。

C.2 本机和云端的关系（建议）

  1. 本机版本在没有云端时也能完整使用，云端功能是附加的。用户已决定这一条。这样开源用户和离线场景都不依赖你的服务器，你的服务器出故障时本机产品也不受影响。
  2. 本机引擎访问云端的代码只放在一个包里，比如 internal/cloud。其他模块通过接口使用它。没有云端时，换成一个“云端不可用”的实现就行。
  3. 云端智能体可以作为协作群的一种成员接入。推断：这和产品“入口型”的定位一致，界面不需要为它单独做一套流程。
  4. 云端的登录令牌由 Go 引擎保存，存进系统的凭据库：Windows 凭据管理器、macOS 钥匙串、Linux 的 Secret Service。界面进程拿不到令牌。据我所知，zalando/go-keyring 能做到这一点且不需要 cgo；这一点不确定，设计时要再核实。
  5. 本机协议不绑定传输方式（见 B.4）。以后如果要用手机访问本机引擎，可以由云端转发。
  6. 哪些数据会发到云端（代码、对话、日志），要逐项列清楚，并让用户主动开启。

C.3 个人开发者的云端起步（建议）

  • 先用一台阿里云 ECS（Linux），上面跑一个 Go 程序，用 systemd 管理进程。
  • HTTPS 用一个反向代理处理，比如 Caddy 或 nginx。据我所知，Caddy 能自动申请和续期证书。
  • 数据库先用阿里云 RDS PostgreSQL，或者 ECS 上的 SQLite 加定期备份。
  • Go 程序编译成 linux-x64 或 linux-arm64 的单个文件，上传后重启服务即可。
  • 一开始不需要 Kubernetes，也不需要拆成多个服务。
  • 云端智能体要调用模型，会产生费用。上线前要先定好每个用户的额度和防滥用规则。

C.4 上线前要查的合规事项（据我所知，不是法律意见）

  • 服务器在中国大陆、用域名对外提供网站或接口时，域名要做 ICP 备案。
  • 面向中国大陆公众提供生成式 AI 服务，适用《生成式人工智能服务管理暂行办法》，可能需要备案或登记。
  • 收集用户个人信息时，适用《个人信息保护法》，需要隐私政策和用户同意。
  • 这些规定会更新。上线前请向阿里云或专业人士确认最新要求。
