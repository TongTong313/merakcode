# Local group coordination

Group startup starts Git-reference and file polling every five seconds. Repository events list new commits and their paths; file events list changed paths. File polling excludes `.git`, `node_modules`, `.merak` and claim workspaces, including active inplace leases. Ending an exclusion establishes a new baseline without reporting claim writes as external edits. Scans stop above 50000 files or one second and emit one `sentinel.flagged` finding with an owner notice (`MRK-1005`). No native watcher dependency is used.

Group settings contain `triggers`: event types, an optional path glob (`**` spans directories), an action and a cooldown in nanoseconds. Actions create a task with the template as its title, notify owners, wake a Leader at priority 0–3, or assign the event's task to a worker. `member` on a create action assigns the new task directly. A cooldown applies to the same rule, group and task and survives live settings updates. Rule outputs do not recursively trigger more actions. Handled facts inform the scheduler without waking the model unless an action explicitly asks to wake it. The default conflict rules create an integration task for the original worker and inform the Leader at high priority.

`group.update` replaces settings and requires admin or owner. Initiative defaults to `normal`: environmental changes inside an active task's area wake its thread and identify a potential conflict; other changes are combined at low priority. `passive` only records environmental events, including events matched by custom rules. `eager` processes unmatched environmental events immediately. Integrated commit IDs and file ownership prevent a task from treating its own delivered work as an external conflict. Human cancellation informs the group thread urgently; a stalled task informs its task thread at high priority.

Worker descendants receive a claim marker through Git's `GIT_REFLOG_ACTION`. The watcher accepts marked commits only for claims in the current group and checks that the reference-log text matches the commit subject. Reset and fast-forward records do not acquire commit ownership. Missing or unrecognized evidence stays external; the watcher never attributes all commits during an inplace lease to its worker. Markers affect reference logs, not commit authors or messages. The scan reads at most 10000 recent reference-log entries.

A local group has a default Leader member. Top-level tasks inherit that Leader unless a different Leader member is specified. Group and member events share the group stream with task and notice events. Worker and Leader conversation events remain in their session streams and carry group, task and member attribution.

The task pool records creation, publication, queuing, start, report and closure. Only Worker members can receive claims. A queued claim has no session until it starts. One active claim per member is allowed; a submitted report frees that member to start the next queued claim. Child agents have no member identity and cannot claim tasks.

Each top-level task has one Leader session and priority scheduler. Subtask events route to the top-level ancestor. Events without a task route to the group thread. Opening a top-level task and submitting a report enqueue work. Progress is combined before delivery. Direct Worker answers inform the scheduler without waking its model. A waiting scheduler does not poll the model.

Task threads can operate only in their own subtree. `set_phase` advances planning, doing and integrating, or records a stall. A configured plan checkpoint waits for human approval before assignment. Integration requires successful reports; review requires completed merges or published artifacts. Final human review is enabled by default. Approval closes children before the goal. Rework keeps original claim IDs, sessions and workspaces. Replanning returns the goal to planning. A final notification is refused until these completion checks pass.

Only the group thread receives `set_task_leader`. Humans change Leaders through `task.update`, which requires admin or owner. Children inherit the replacement Leader. The previous thread stops before one bounded summary request, then `thread.handed_over` records both session IDs and the summary. The replacement's first input contains that summary, its task card and current group state. Summary generation does not block other threads; pending events transfer to the replacement. A failed summary explicitly directs the replacement to inspect the prior session.

Recovery restores persisted thread identities and conversations. A Leader change saved before its handover resumes that handover after restart. Recovery leaves active group sessions running and does not replay interrupted tool calls.

Builtin workers receive `submit_report` and `report_progress`. Reports reject summaries over 1200 Unicode code points with a reason. An accepted report ends the turn after paired tool results. Without a report, the worker receives one reminder turn; a second omission produces a synthesized report from the last nonempty answer. Progress accepts one line up to 300 code points.

The Leader state keeps goal, task and member tables. Every group change saves a document with the last group sequence. Rendering retains IDs, focuses detailed rows on the current task subtree, and shortens text to fit the requested budget. A budget smaller than the irreducible IDs cannot contain the state; the session request budget remains the final limit. The scheduler digest includes the rendered state, event ID and bounded task event payload, not the Worker's conversation history.

Group creation includes initial members and their profiles. Profiles already stored under the same ID can be reused unchanged. `task.update` changes a Leader or phase; `task.cancel` requires admin or owner and closes unfinished descendants. Cancellation stops active claims and leaves their history available. Stalled goals preserve their previous phase and stop queued claims; restoring that phase resumes the queue. Failed dependencies stall dependent goals and notify owners.
